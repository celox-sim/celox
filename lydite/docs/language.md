# lyd: a language for state transitions and verification contracts (0.9)

For 0.7 `specification` documents (composition of relational specs, positive/negative examples, limited binding), see
[relational specifications](specifications.md). The
version 2 `design` language and semantics on this page remain compatible.
For 0.9 primes, named expectations and quantified traces, see [expectations and traces](expectations.md).
For version 4, with local ports, explicit wiring and independent operation sets, see
[scoped specifications](scoped-specifications.md).

`.lyd` uses a parser generated by parol 5.0.2. The grammar is
`crates/lydite-syntax/src/lyd.par`. The generated AST is not used as the solver data structure; it passes through a
frontend that tracks source locations and produces the same typed `lydite_ir::Design` as JSON input.
JSON remains as the existing input/output and compatibility-checking format.

## Examples to read first

- [memory_increment_readable.lyd](../examples/memory_increment_readable.lyd): a short hand-written example.
  It uses typed literals, if/else, array indexing and operators, and updates memory at an arbitrary address three times
- [auto_array_sum.lyd](../examples/auto_array_sum.lyd): a migration of the existing sum contract
- [array_sum.lyd](../examples/array_sum.lyd): a sum with a manual partition
- [memory_increment.lyd](../examples/memory_increment.lyd): a migrated version that makes the old JSON tree structure explicit

The hand-written and migrated memory examples convert to exactly the same JSON document. The extra scalar
is there to exercise the partitioning heuristics and is not an essential part of the memory design.

```
cargo run -- examples/memory_increment_readable.lyd --check
cargo run -- examples/memory_increment_readable.lyd --emit-json /tmp/memory.json
cargo run -- examples/auto_array_sum.lyd --out /tmp/sum --z3 /path/to/z3
cargo test --workspace --locked
cargo install --path ../crates/lydite --locked
```

`--check` and `--emit-json` only check syntax, names, types and the like, and never report a proof.
A normal run also does not start Z3 before these checks complete. The `.lyd` extension is detected automatically,
and `--format lyd` / `--format json` can be given explicitly. The existing JSON execution format is retained.

## Language structure

Start the document with `design "name"`, followed by declarations.
The header has no trailing semicolon, and no braces enclose the whole document.

- `input rst: bool;`, `input data: mem<8, 8>;`: shared inputs
- `reset_input rst;`: name of the synchronous, active-high, highest-priority reset input
- `spec { ... }`, `impl { ... }`: the two machines
- `binding expr;`: the relation between abstract and implementation state
- `commit output_name;`, `can_step output_name;`: designate Boolean outputs of impl / spec
- `hold_when expr;`: the condition under which hold is required (optional)
- `progress { enabled expr; rank expr; }`: progress conditions for noncommit steps
- `contract { ... }`: program contract (optional)

A machine contains state declarations such as `state count: bv<4>;`, plus `reset`, `next`,
`outputs` and optional `wires` blocks. Assignments are written inside a block as `name = expr;`.
reset/next give every state exactly one value each. Assignment order does not imply sequential execution.
Every next expression reads the pre-update state. An omitted assignment is not interpreted as an implicit hold.

Names consist of ASCII alphanumerics and `_` (not starting with a digit). `if` / `else` / `true` / `false` are reserved.
`design` / `specification` select the document kind at its start and may also be used in identifier positions.
Declaration keywords such as `input` / `state` / `parameter` are also interpreted by context and are not new reserved words.
For example, `input state: bool;` declares an input named `state`.
`.` in a reference is a namespace separator.
`i.x` is an input, `s.x` inside a machine is that machine's state, and `w.x` is a wire.
Bindings use `spec.x` / `impl.x`; program contracts use `s.x` / `p.x`.
The available namespaces are restricted per role. Wires must be acyclic combinational expressions.
Duplicate declarations, assignments, sections and properties are errors rather than overrides.

## Types and expressions

- `bool`
- `bv<N>`: a 1–64 bit word
- `mem<A, W>`: a memory from A-bit addresses to W-bit words
- `255u8`: value 255, width 8. Values exceeding the width are interpreted modulo, as in the existing IR
- `bv(8, -1)`: 8 bits, all ones. Negative numbers must be within the signed 64-bit range
- Bare numbers are used only for numeric arguments such as those of bv / extract / extension / range
- `true`, `false`
- `if cond { expr } else { expr }`: both branches have the same type
- `memory[address]`: same as `read(memory, address)`
- `write(memory, address, value)`: returns the updated memory value. It does not modify state within the expression

Typical examples:

```
count = if s.count != 0u4 { s.count - 1u4 } else { s.count };
mem = write(s.mem, s.address, s.mem[s.address] + 1u8);
```

Precedence, from tightest to loosest, is as follows. Binary operators are left-associative.

1. Calls, indexing, parentheses
2. `!` (Boolean negation), `~` (word inversion), unary `-` on numeric arguments
3. `*`
4. `+ -`
5. `<< >>`
6. `== != < <= > >=`
7. `&`
8. `^`
9. `|`
10. `&&`
11. `||`

Chained comparisons are not allowed. `a < b < c` is an error; write `a < b && b < c`.
`< <= > >=` are unsigned. For signed comparison use `slt(a,b)` / `sle(a,b)`.
`& | ^ ~` operate on fixed-width words and `&& || !` on Booleans. There are no implicit conversions across types.
Unary `-` is limited to bare integer arguments. For words, use subtraction: `0u8 - x` or `sub(0u8,x)`.

IR operations can also be written in call form:
`bv`, `const_mem`, `extract`, `zext`, `sext`, `not`, `bnot`, `and`, `or`,
`xor`, `implies`, `eq`, `ne`, `ite`, `add`, `sub`, `mul`, `band`, `bor`,
`bxor`, `shl`, `lshr`, `ult`, `ule`, `slt`, `sle`, `read`, `write`, `concat`.
The word width of `const_mem(address_width, value)` is determined by the type of value.
The ranges of `extract(high, low, word)`, `zext(amount,word)` and `sext(amount,word)` are also checked.

## Program contracts

A `contract` contains `parameter name: type;`, `pre`, `invariant`, `terminal`,
`post` and `rank`. Their meaning is the same as in the existing [JSON schema](schema.md).
`precondition` / `postcondition` are aliases for `pre` / `post`.

Automatic partitioning is the default. It can be stated explicitly with `partition auto;` or `partition none;`.
A manual partition has the following form; min/max are inclusive.

```
split {
  pc = range(s.pc, 0, 2);
  index = range(s.idx, 240, 255);
}
```

`cases { name = Boolean_expr; }` can also be used. Combining automatic and manual specification is forbidden.
`range` is only for split and is not an ordinary word operation.

## Compatibility and migration of existing sources

The 0.8 individual-declaration forms do not change version 2 / 3 JSON or the verification semantics.
The extensions for local ports, explicit wiring and independent operations are used in separate version 4 documents.
The outer braces of the old `design "name" { ... }` / `specification "name" { ... }`,
`inputs { name: type; }`, `state { name: type; }` and
`parameters { name: type; }` remain available as compatibility forms.
Even when old containers and individual declarations are mixed, the same name cannot be declared twice.
For individual declarations and compatibility forms in relational specs, see [relational specifications](specifications.md).

If there are no input, state or contract parameter declarations at all, the DSL allows that declaration group to be omitted.
Lowering fills in `{}` for the corresponding JSON `inputs` / `state` / `parameters`.
In JSON input these required keys cannot be omitted. Omission does not relax semantic checks;
for example, the Boolean input named by `reset_input` must actually be declared.
Required blocks such as `reset` / `next` / `outputs` are still needed as before.

When migrating from JSON, a printer that preserves expression trees and literal values is available.

```sh
python scripts/json_to_lyd.py examples/array_sum.json /tmp/array_sum.lyd
cargo run --locked -- /tmp/array_sum.lyd --emit-json /tmp/array_sum.json
```

The printer emits the new forms for each of v2/v3/v4 and performs no semantic conversion across schema versions.
Bound variables are printed without prefixes. Version 4 bound variables that collide with output names are
renamed, declaration and references together, to unused names (quantifier order, types and meaning preserved).
Acceptance and type checking are done by the Rust parser/validator.
`--infix` prints only the supported operations in parenthesized infix notation.

## Diagnostics and trust boundaries

Syntax errors, duplicates, undefined names, mixed types, width mismatches, wire cycles, malformed contracts and the like are failures.
Even if parol recovers from errors, input that contained errors is never run as a success.
Locations keep a UTF-8 byte offset plus a 1-based line and a column counted in Unicode scalars.

In the library, `parse_document(source, filename)?.validate()?` yields a typed Design.
`ParsedDocument` is editable syntax-side data, so it must not itself be treated as a
validated Design. The whole document is always checked when a Design is constructed.

This version does not provide modules/imports, user functions, type inference, generics, or implementation synthesis from specs.
The parser and lowering are also trusted; there is no formal proof of general compiler correctness.
Selected examples check that the JSON and DSL documents agree with each other and with the generated SMT obligations and verification results.

## Native lemma proposals

A `design` can contain a `proof { ... }` block. A separate
`lemmas "Name" { ... }` module can be attached with `--lemmas FILE.lyd`.
Both forms lower to the shared typed candidate API and require fresh checked
proofs; they do not add assumptions to the model. The surface supports typed
`forall`, direct variable names, `impl.x'`/`spec.x'`, guarded `lemma` proposals,
explicit dependencies, and `use`. `--check` validates candidate names and widths
without proving claims. See the [native authoring guide](lemmas.md)
and [complete counter example](../audit/lemma_candidates/counter.lyd).
