Taxi / cocotb comparison ​

The Taxi / cocotb tab on the benchmark dashboard compares Celox with Verilator using unmodified, self-checking upstream SystemVerilog designs and Python testbenches. The Taxi Benchmark workflow runs daily at 03:17 UTC (12:17 JST) and supports manual dispatch. Only a successful scheduled or manual master run publishes history.

The manifest pins fpganinja/taxi to cc70b270b910d369ab1ad7b3855e76399fd461f1, including sources, tops, parameters, expected test counts and random seed 12345. The Python requirements are pinned; CI uses Ubuntu 26.04, Python 3.13, cocotb 2.1.0 and Verilator 5.052. The local setup action builds Verilator from the fixed upstream commit ea338be98e1e838d3518809ce8899f85a009963c on the runner. Its installation cache is separated by Ubuntu version, architecture, compiler, libc and build recipe. Cache hits still verify the installed version and source identity. Each configuration has a six-hour job limit and a one-hour limit per compiler or simulator process; RX configurations run the complete test matrix three times per simulator.

These are five fixed configurations, totaling 472 tests per simulator per sample, rather than the entire Taxi project's parameter matrix. Each daily run executes three samples of each configuration for each simulator.

Measurement ​

Each configuration gets one VM. Both engines compile and run sequentially on the same logical CPU, alternating Celox/Verilator then Verilator/Celox. The third pair runs in the first order again. Different configurations can use different CPU models. CPU model, runner, boot ID, tool versions, CLI binary hash, source hashes, parameters, commands, logs, XML and every raw timing are retained in the taxi-* artifacts for 30 days. The dashboard separates CPU models.

The charts show three distinct measurements:

  • Test body: median of three sums of cocotb XML test times. This includes Python stimulus, resets, simulator interaction and assertions. Cocotb 2.1.0 uses time.monotonic() for its test durations. A shared GPI startup check verifies the pinned version without replacing its clock, measurement boundaries or XML writer. Wall-clock corrections cannot corrupt elapsed times. It measures the usable cocotb workload, including Python overhead.
  • Whole process: median of three fresh executable processes, from spawn to exit. Celox's Python discovery and result checks are inside this interval; Verilator's Python environment is configured beforehand. Both retain Python initialization and simulator startup. Compiling the RTL is excluded.
  • HDL compilation: one fresh build per engine, before any runtime samples. Celox includes frontend analysis, native code generation and attached executable writing. Verilator includes RTL-to-C++ generation and serial C++ compilation. C++ compiler caching is disabled. Building Celox itself and installing tools are excluded.

Celox uses native O1 and two-state execution. Verilator uses cocotb's standard --vpi --public-flat-rw adapter and its default C++ -Os setting. Tracing is off for both. RX32 explicitly uses 1ns/1fs in both builds. Diagnostic relaxations are explicit in the runner. Both simulators receive the same unchanged source bytes and parameter values.

Every sample must contain the expected number of unique, passing tests. Skips, missing XML, duplicate identities, invalid timings, nonzero exit, timeout, or unequal per-test simulated durations fail the run. Any failed configuration prevents the daily set from publishing. A failed run cannot add zero or partial performance points. Prior successful history remains visible with its original date. The raw report also records the median of paired Celox/Verilator body-time ratios; values below one favor Celox. This differs from dividing the two medians. Shared CI machines introduce noise; repeat small differences before drawing performance conclusions.

Run locally ​

bash
python3.13 -m venv work/taxi-venv
work/taxi-venv/bin/pip install -r benchmarks/taxi/requirements.txt
cargo build --locked --release -p celox --bin celox
work/taxi-venv/bin/python scripts/run-taxi-bench.py prepare work/taxi-source
work/taxi-venv/bin/python scripts/run-taxi-bench.py run phy64 work/taxi-source target/release/celox work/taxi-phy64

Install Verilator 5.052 and a C++ compiler first. Choose a fresh output directory for every run; existing results are never reused as a new measurement. Use --samples 1 for local integration checks; daily publication requires all three samples. Results from a locally modified checkout are diagnostics, not published benchmark evidence.
