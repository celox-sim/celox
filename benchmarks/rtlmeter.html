RTLMeter ​

Open the RTLMeter dashboard.

The comparison runs the unmodified XuanTie-E902, XuanTie-E906 and HummingbirdV2-E203 hello programs from RTLMeter, fixed at commit 4fdd6c3fd154e9b99d3a9d713cf3f4977e284f94. The manifest also registers Servant and XuanTie-C906 hello for the completion and cycle-count qualification check; they are not part of the daily timing comparison below. All tools receive the same ordered source list, headers, defines, testbench and firmware (case.pat for E902/E906; program.hex for E203). E203 uses the upstream default configuration, including its #1 flip-flop delays, with assertions enabled and standard shared-variable semantics. Input hashes, tool versions, executable hashes and raw output are retained with each run.

State models ​

2-state and 4-state have separate charts and qualification tables. Every supported configuration must first pass a probe for uninitialized logic and an undriven wire. The 2-state probe expects zero; the 4-state probe expects X/Z.

Simulator2-state4-state
Celox tiered with hotspot JIT, O2, one thread--two-state--four-state
Verilator 5.054, C++ -O3, one build worker--no-fourstate --x-initial 0 --x-assign 0--fourstate, experimental
xezim, stable release pinned by NixUnsupported: no global 2-state modeDefault VM, persistent caches disabled

Celox runs celox run --backend tiered --jit hotspot: simulation starts on the interpreter immediately, and frequently executed groups switch to native code as background compilation finishes. Earlier points used the native backend, which compiles the whole design before simulation starts; account for this when comparing history.

Verilator documents --fourstate as experimental and for developer use. See its option reference. xezim's zero-initialization settings change initial values, rather than selecting 2-state semantics; they are not used as a substitute.

Measurement and acceptance ​

Each point is the median of three fresh cold source-to-finish measurements. The timer includes HDL parsing, elaboration, compilation, startup and execution. For Verilator it includes both C++ generation/build and the resulting executable. Every sample uses a fresh build directory; persistent simulator/compiler caches are disabled. Temporary C++ artifacts are deleted after each measurement. Simulator installation and building Celox itself are excluded. These short programs measure iteration latency, not steady-state simulation throughput.

All configurations for one design run sequentially on the same VM and logical CPU, with tool order rotated between repetitions. Different designs may run on different hosts. Compare results within one design, state model and host.

A successful sample requires a zero exit status, the expected program output and success marker exactly once, no failure marker, and a positive final RTLMeter clock count. E902/E906 print Hello Friend! and TEST PASSED; E203 prints Hello World from HummingbirdV2 E203 and TEST_PASSED. Servant prints Hi, I'm Servant! and Test complete; C906 prints Hello Friend! and TEST PASSED. Counts must be stable across repetitions and differ by at most one clock between tools, allowing for $finish and the counter on the same active edge. A separate one-cycle negative control must stop before program success. All tools use the same upstream +max_cycles limit (16,384 for E902/E203/C906; 32,768 for E906; 131,072 for Servant), so a stalled UART or CPU cannot count as a completed workload. Unsupported modes, probe failures, simulation failures, timeouts and clock mismatches appear in the table and contribute no performance points.

The RTLMeter Benchmark workflow runs daily at 04:37 UTC and by manual dispatch. Only scheduled/manual master runs publish history. Raw logs remain available in workflow artifacts for 30 days.

Steady-state simulation throughput ​

In addition to cold process latency, steady-state simulation throughput is measured using CoreMark on XuanTie-E902 and XuanTie-E906 under the rtlmeter-steady-state-v1 contract (benchmarks/rtlmeter/steady_manifest.json).

SimulatorConfigurationSimulation measurement
Celox--backend native -O O2execute_ns from CELOX_TEST_TIMING
Verilator-O3 -CFLAGS -O3Elapsed wall time of the compiled simulator binary
xezimRelease VM, --verbose[PHASE] simulation: elapsed time

Pure simulation execution time is isolated from compiler elaboration, reporting both simulation execution time (us) and simulation clock throughput (cycles/sec, kHz). The RTLMeter Steady-State Benchmark workflow runs daily at 05:17 UTC.

Reproduce ​

Build the CLI in the repository development shell and use the xezim shell:

sh
cargo build --locked --release -p celox --bin celox
mkdir -p work/rtlmeter-bin
cp target/release/celox work/rtlmeter-bin/celox
python -m venv work/rtlmeter-python
work/rtlmeter-python/bin/pip install -r benchmarks/rtlmeter/requirements.txt
work/rtlmeter-python/bin/python scripts/run-rtlmeter-bench.py prepare work/rtlmeter-source
nix develop .#xezim --command work/rtlmeter-python/bin/python scripts/run-rtlmeter-bench.py run e902 work/rtlmeter-source work/rtlmeter-bin/celox work/rtlmeter-report

Repeat with e906 or e203 and a fresh output directory. Local dirty-checkout results are useful for investigation and cannot be published as release measurements.

Profile a case per clock ​

scripts/rtlmeter-profile.py explains where the work of a case goes, per RTL clock, and compares two builds on the same input. It uses the steady-state command line of the case and needs the same Python environment:

sh
work/rtlmeter-python/bin/python scripts/rtlmeter-profile.py run e902 \
  --celox work/rtlmeter-bin/celox --out work/profile/e902-before --sample
work/rtlmeter-python/bin/python scripts/rtlmeter-profile.py run e902 \
  --celox work/candidate/celox --out work/profile/e902-after --sample
work/rtlmeter-python/bin/python scripts/rtlmeter-profile.py compare \
  work/profile/e902-before work/profile/e902-after

run runs the case several times and checks that every run reaches the same clock count and prints the same program output:

  • A profiled run uses celox run --activation-profile FILE. The compiled scheduler counts what each part of a time slot did: its slots, the domain judgments of each wave and how many found no edge, the units of each clock domain, each kernel's runs and the edges it gave, each request of the settle by what requested it, the settle's runs and skips with the cause (inputs, clock or time only, published values), the groups of an event-driven settle, the observers, and the partitions of a partitioned settle with the runs that changed nothing they compare.
  • A clean run has no counters. Its CELOX_TEST_COUNTERS line (--report) gives the user instructions and cycles of the execute phase alone, without compilation: the totals to judge a change by. The report also says how many instructions per clock the counters added to the profiled run.
  • With --sample, a sampled run records user instructions with perf record and CELOX_PERF_MAP=1. The perf map names every native function, and an outlined body of the compiled scheduler is named after the domain, kernel or settle group it runs, so the report gives instructions per clock, activations per clock and instructions per activation of each of them. disasm RUN_DIR [--match TEXT] prints the machine code of the hottest blocks of that same run (CELOX_PERF_MAP saves the mapped code as /tmp/perf-<pid>-<address>.bin, which run moves next to the samples).

compare lists the totals per clock of both runs, the roles whose instructions per clock changed the most (with their activations and cost per activation), and the activation counters that changed the most per clock. A counter that grows tells which work started more often; a cost per activation that grows tells which work got slower. verilator CASE --out DIR measures the Verilator model of a case under perf stat for a whole-process upper bound of its instructions per clock.

scripts/activation-profile.py show FILE and diff BEFORE AFTER read the profile files directly, normalizing per clock with --cycles, the _rtlmeter_cycles.txt of the run, or the runs of the most frequent domain.
