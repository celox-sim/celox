SystemVerilog Conformance and Deviations ​

For setup and a first simulation, start with SystemVerilog Support.

Baseline: IEEE 1800-2023 ​

Celox implements SystemVerilog as specified by IEEE Std 1800™-2023. This page does not restate the standard. It organizes every difference into five categories:

  1. Unsupported features — entire constructs or clauses not implemented and rejected at compile time.
  2. Partially supported features — features where Celox implements a specific subset; each table states Supported and Not supported side by side.
  3. Narrow limitations — specific edge-case restrictions in features that otherwise follow the standard.
  4. Intentional deviations — split into deviations affecting standard-conforming code and permissive acceptance of non-standard code.
  5. Implementation-defined choices and the Celox execution model — tool choices where the standard leaves behavior unspecified, plus Celox's Rust Simulator / Simulation split, host clocks, multiple top modules, checkpoints, memory files, mixed-language designs, and DPI-C registration.

Conformance scope: standard vs. non-standard code ​

  • Standard-conforming code: Valid IEEE 1800-2023 code that does not rely on any construct, limit, or deviation listed on this page executes as the standard specifies — or, if a feature is unimplemented, fails at compile time with an Unsupported diagnostic naming the construct and its tracking issue (or the frontend roadmap #88) rather than silently mis-simulating. Any unlisted difference on valid standard code is a bug; please file an issue.
  • Non-standard code (default mode vs. strict mode): Accepting non-standard code is less severe than mis-simulating valid standard code, so default mode intentionally accepts several common compatibility relaxations with warnings (see Permissive acceptance of non-standard code and [diagnostics]). In strict mode (strict = true / --strict / .strict(true)), those compatibility diagnostics become errors; accepting any non-IEEE 1800-2023 code in strict mode (outside the explicit extensions documented below) is a bug — please file an issue.

Measured conformance is published on the verification page.

Unsupported features ​

These constructs and clauses are not implemented and are always rejected at compile time (except the one declaration-only covergroup case noted below):

  • Verification and design-level blocks: bind, checker, config, covergroup (a class may declare a covergroup that nothing constructs; constructing one or calling its methods is rejected), clocking blocks and clocking drives, user-defined primitives (UDP), and specify blocks.
  • Port forms: ref ports (#427).
  • Unions and mixed array/container types: tagged unions, unpacked unions, packed union assignment patterns, fixed-size unpacked arrays of chandle (chandle a[4], including via typedef), fixed-size unpacked arrays of dynamic containers (int a[2][$], including via typedef), and dynamic containers of fixed-size unpacked arrays (int a[][2]).
  • Control flow: disable statements other than disable fork; fork inside declaration initializers, final, always_comb, and always_ff (no process scheduler in those contexts).
  • Timing and system tasks: wait_order, and any unimplemented IEEE 1800-2023 or Annex D system task/function. Celox knows every standard name and reports unsupported ones by name wherever written, including in unused parameters and function bodies (e.g., $get_coverage).

Narrow limitations in otherwise supported features ​

  • Design structure:
    • Non-ANSI port expressions such as module m({a, b}, c[3:0], .p(d)) (#1953); plain non-ANSI ports (a header of port names with body declarations) are supported.
    • Non-constant ANSI input port defaults (23.2.2.4), defaults on non-input ports, and unpacked-structure port defaults; constant singular input port defaults are supported (constant unpacked-array input port defaults warn via unpacked_port_default, rejected in strict mode).
    • Implicit nets declared by port connections of an instance inside a generate block (6.10): an input connection reading one is rejected, and one driven only by outputs becomes a net of the module rather than of the block.
    • Instance arrays that are multidimensional, have a negative bound, or exceed 4,095 elements.
    • Package nets (#1146); a package variable cannot be a clock or reset.
    • Wildcard imports (26.3): a module, interface, program, or package scope, a generate block, and a procedural block each bind a name once for their whole body (export p::x; binds it in the package), not per reference. References covered by one binding that denote different declarations at their positions are rejected; a block-local initializer reading a package variable through the block's own wildcard import is also rejected (#4350).
    • Only one source file may declare $unit variables.
  • Types and expressions:
    • Enum methods (first, next, …) on an element of a packed array of enums (#2417).
    • Constant out-of-range part-select reads, and constant out-of-range part-select writes to an array element or an inner packed dimension (#88). Partial out-of-range constant writes to plain packed vectors (e.g., q[9:6] = v on logic [7:0] q, writing only q[7:6]) and all run-time selects follow the standard.
    • Run-time part-selects and element selects of a member of an element of a packed array of structures that is itself a member of a packed structure, such as s.regs[i].q[j +: 4].
    • Reduction operators in parameter expressions (#456).
    • Type operator (6.23): comparing a type reference with a value, range items in a case on a type, and applying type(...) to an expression that reads a port or to any expression in a generate block.
    • $typename (20.6.1): rejects types without one exact spelling instead of inventing system-generated names — anonymous enumerations, structs, and unions, soft and tagged unions, unpacked structures with unpacked array members, packed arrays of enumerations or of signed typedefs, classes with non-integral value parameters, and operands other than names and data types (such as $typename(a + b)). Virtual interface types (unspecified in 20.6.1) are written as declared (virtual bus_if, virtual bus_if.mp, virtual bus_if#(8, 4)).
    • Aggregate parameters as elaboration-time constants: unpacked array parameters hold their value from simulation start; an element of a 1D array parameter (and a select of its packed dimensions unless the element type is a packed array of a signed named type) is an elaboration-time constant only when elements are packed integrals ≤ 127 bits without X/Z bits and the array has ≤ 4,096 elements; a member of a packed-struct parameter is an elaboration-time constant unless wider than 127 bits or containing X/Z bits; whole unpacked arrays and other elements/members cannot be used where an elaboration-time constant is required.
  • Processes and subroutines:
    • Nonblocking assignments inside always_comb (#453) and always_latch (#431); use blocking assignments there.
    • Package and $unit timed tasks with static arguments.
    • Constructing or extending the built-in process class; suspending a process's own thread or calling await() from a function.
    • Loops: procedural loops unroll at most 10,000 iterations; combinational loops with a run-time trip count must be counted for loops; loop-generate constructs within one module are rejected past 1,000,000 iterations in all; genvar updates using bitwise compound operators (#455) and recursive constant-function expansion in generate constructs are rejected.
    • final procedures : timing controls, calls to user tasks (including through functions), and functions that schedule events after returning (13.4.4) are rejected; detached fork … join_none children declared in a final procedure are initialized but never start (see Execution model).
    • Named subroutine arguments: calls whose selection indices have procedural effects, and method defaults using the receiver in an always_comb or assign call when the receiver or an earlier argument reading the object has effects.

Intentional deviations ​

Deviations affecting standard-conforming code ​

These accepted IEEE 1800-2023 constructs deliberately behave differently from the standard. Portable code should avoid relying on them:

  • Program continuous assignments do not run in the Reactive region. Continuous assignments in a program are evaluated with the design's combinational logic, and design logic that a program writes settles while the reactive region set runs, so a program resuming after #0 reads the new values. IEEE 1800-2023 4.5 evaluates them only once the reactive region set is empty. Icarus, Verilator, and xezim behave as Celox does.
  • Static storage of interface subroutines across modules and virtual interfaces. A static function or task called through interface ports of several modules keeps its static variables, and the static formals of a task that suspends, once per calling module instead of once per interface instance (13.3.2, 13.4.2; #3739). Calls through the instance itself and through the port of a single module share one. Likewise, a task or function called through a virtual interface (vif.drive(req), 25.9) holds static variables per calling scope, and formals belong to each call (even on static subroutines).
  • Procedural assign override timing on indirect writes. While a procedural assign is active, a write to its variable other than by a plain assignment statement (an output argument, a concatenation target, a delayed nonblocking assignment, or a hierarchical name in another module) is overridden in the time step it happens rather than suppressed, so a process waiting on the variable can observe the written value.
  • Run-time %p format strings simplify non-string values. When a %p conversion comes from a format string evaluated at run time rather than a compile-time literal, Celox prints string values in quotes and any other value as %0d.
  • Coverage is not reported. Immediate cover executes its pass statement, but coverage counters and reports are not exposed.
  • $exit outside a program warns. A $exit call from anywhere other than a program thread is ignored, as 24.7 specifies, and Celox also reports a compilation warning (exit_outside_program in [diagnostics]), including for calls in unused function declarations.
  • UVM DPI functions are built in. Imports with the C names of UVM's src/dpi functions bind to Celox's implementations instead of a user C function; see DPI-C imports.
  • Opt-in compatibility modes. Options in [compatibility] (such as legacy_empty_reductions and shared_always_temporary) preserve standard IEEE 1800-2023 semantics by default and deviate only when explicitly enabled.

Permissive acceptance of non-standard code ​

Celox intentionally accepts the following non-standard constructs and compatibility extensions. Portable code should avoid relying on them.

Warn by default, rejected in strict mode (strict = true / --strict / .strict(true)):

  • A missing static keyword on initialized locals (6.21). IEEE 1800-2023 6.21 requires an explicit static when a static variable's declaration specifies an initializer. Celox also accepts the declaration without static with a constant initializer in any procedure, and with a run-time initializer in a procedure that runs once (such as initial), reporting an implicit_static_initializer warning (warn by default, error in strict mode). In an always procedure, a run-time initializer without static or automatic is rejected.
  • Default time scales when explicit time scales are mixed (3.14.2.3). Instead of rejecting designs where only some elements specify or inherit a time scale, Celox reports a mixed_timescale warning (error in strict mode) naming those elements and assigns them 1 ns / 1 ps, as other simulators do.
  • Other warn-by-default compatibility diagnostics. Duplicate module declarations (duplicate_module), $size on fixed-size interface arrays (interface_array_query), bus.WIDTH parameter shorthand on interface arrays (interface_array_parameter), constant unpacked-array input port defaults (unpacked_port_default, 23.2.2.4), and memories shared between always_ff and another edge process (multiple_always_ff_drivers) warn by default and are rejected in strict mode; see [diagnostics] (alongside inferred_latch).

Accepted even in strict mode (intentional extensions):

  • Packed values and unbased fills assigned to fixed-size unpacked arrays (7.6). Celox accepts assigning a packed value of the exact whole-array bit width (bit for bit) and filling every element with an unbased unsized literal such as '0. Values of any other width, real, or string are rejected.
  • Procedural force on variable selects and unpacked array elements (10.6.2). Extends force beyond vector nets to constant bit/part-selects or members of variables, and constant-indexed elements (or constant selects/members) of fixed-size unpacked arrays of packed integrals (emitting forced_array).
  • $psprintf is accepted as $sformatf. The vendor system function $psprintf is accepted as $sformatf (21.3.3); diagnostics name it $sformatf.

Implementation-defined and unspecified behavior ​

Where IEEE 1800-2023 leaves a choice to the implementation, or declares an order unspecified or nondeterministic, Celox chooses as follows. Portable code must not depend on these choices.

Constant widths ​

IEEE 1800-2023 lets an implementation limit the width of a vector to no less than 65,536 bits (6.9.1, 7.4.1). A constant value, such as a parameter, the concatenation that gives it or a part-select of it, may have up to 1,048,576 bits. A replication, a constant built bit by bit, and a value inside a constant function call may have up to 65,536 bits. A wider constant is rejected before it is built.

Event scheduling ​

Clause 4.7 permits either order in the cases below; Celox is deterministic:

  • Continuous assignments, combinational processes, and event expressions see a timed process's writes when that process reaches a timing control or ends. After b = 1; a = 1;, a ^ b has not changed, and a pulse a = 1; a = 0; wakes @(a) but not @(a ^ b); write #0 between the writes to make the pulse visible to an expression wait. Compound waits on fork-shared automatic locals instead observe each supported blocking assignment and statement-call copy-out.
  • A waiter sees every value one evaluation of always_comb, always @*, or an edge-triggered process writes, including one a later write overwrites (4.3, 9.4.2). Through a child instance's output port — a continuous assignment (23.3.3) — a waiter in the parent sees only the settled value.
  • An expr iff condition item (9.4.2.3) is judged at each write of expr when both are variables, so in one process clk = 1; en = 0; is an event and en = 0; clk = 1; is none. When expr or the condition is a general expression or a net, or expr is written by a flip-flop domain (#1830), the condition is judged when the occurrence is detected, after combinational logic settles.
  • A wait condition reading class properties is re-checked after any store of a property it reads — through any handle and after every randomize() call — including stores of the same property of another object or of the value already held, so it may be checked more often than the minimum (9.4.3).
  • With an asynchronous reset, a $past history tick is a run in which the clock has left the level it had before the time slot; a clock that returns to that level within the slot does not move the history. Multiple clocking-event transitions within one time step are undefined in concurrent assertions (16.5).

Time and precision ​

  • The implementation default time scale is 1 ns / 1 ps. A Simulation counts time in the design's global time precision (3.14.3), 1 ps by default, so %t reports picoseconds in a design without time scales.
  • $timeformat (20.4.3) sets the units, decimal places, suffix and minimum field width of the %t conversions after it, in every output and in $sformatf; the time rounds half away from zero, and the width of a conversion such as %0t replaces the minimum field width. The suffix is a string literal, NUL characters included. An always_comb, always_latch or always @* that calls it, also through a subroutine, runs as a process: once at time zero (except always @*), then after each change of what it reads. A units number outside 2 to -15 or a negative precision or field width computed at run time ends the simulation with an error, as a constant one fails the analysis; Celox prints at most 4,096 decimal places and pads to at most 4,096 characters, and a larger precision or field width is an error.
  • A class or subroutine declared in the compilation unit ($unit) uses the compilation unit's time unit and precision. A `timescale directive does not set those (3.14.2.3), so they are the default 1 ns / 1 ps unless $unit declares timeunit/timeprecision. Verilator applies the last `timescale instead. For portable code, declare timeunit in $unit. A precision finer than the global precision rounds to whole simulation steps.
  • final procedures run sequentially in a deterministic but unspecified order. Relative order of package and module variable initializers that call constructors or functions is likewise unspecified (6.8, 10.5); do not rely on it.

Random numbers ​

  • $urandom uses a deterministic 32-bit linear congruential generator (18.13.1, 18.14); its default seed and sequence are implementation-defined and need not match other simulators. $random and the $dist_* functions follow Annex N, so their sequences match other implementations of that annex. The random-state strings of process and of class objects (get_randstate, 18.13.4) are opaque and specific to Celox; set_randstate (18.13.5) accepts only a string that get_randstate returned and otherwise ends the simulation with an error.
  • In combinational procedures, random draws occur when the process activates; repeated evaluation with unchanged inputs does not advance the stream.
  • Constrained randomize() searches for a satisfying assignment with the object's seed and updates all selected properties together; the search does not guarantee a uniform distribution (#2187). Proved infeasibility returns 0, preserves the properties, and skips the post-hook (18.6.3); resource exhaustion is a runtime error.
  • Soft constraints (18.5.13) are tried from the highest priority down (18.5.13.1): each is kept when the hard constraints and the soft ones kept before it allow it, and is otherwise discarded; a disable soft discards the lower soft constraints that name its variable (18.5.13.2). The search for each keeps the seed, so the choice is reproducible. A soft dist constrains its operand to its items of nonzero weight; while it is kept, its weights shape the choice as those of a hard one do (18.5.3), and a discarded one has no effect on it.
  • A 4-state rand property takes a 2-state value. The X and Z bits of a 4-state state property, of the value of a function a constraint calls whose type is 4-state, and of a 4-state caller-scope input of inline constraints or of std::randomize() with, follow the 4-state semantics of each operation (11.4): a constraint or guard whose truth they decide ends the simulation with an error (18.3), one they do not decide, as through a mask, a select or an && a known 0 decides, takes its value, and such a guard is evaluated before solving (18.5.13). Where the truth also depends on random variables, the solution found decides whether they reach it.
  • solve before (18.5.9) leaves the solutions as they are, and the search does not order its choices by it; a circular order is not diagnosed.
  • A function a constraint calls (18.5.11) runs as any call of it does, the override of the object's class included, after the random variables in its arguments are solved by the constraints that name only them; its value is state to the other constraints, so they can leave the call no solution, and a random variable it reads that is no argument has its value before the call.
  • randsequence (18.17): a production of several rules picks one by their weights, 1 unless given, from the thread's random number generator (18.14.2). rand join interleaves its productions' items at random from the same generator; 18.17.5 gives the bias no formula, so Celox evaluates it once and, at each step, with probability |2 × bias − 1| advances a production with the fewest items left (bias below 0.5) or the most (above 0.5), and otherwise any production with items left, each as likely (0.5 prefers no length; 0.0 and 1.0 always prefer the shortest and longest).
  • Array shuffle draws from the calling process's random stream.

Host-dependent results ​

  • $ferror codes and wording are host dependent; Celox also exposes a failed $fopen's details through FD 0.
  • $system returns the C system() value, including the host platform's exit-status encoding (20.17.1). Relative file paths use the host process's working directory.
  • $fgets with no bytes read leaves the destination unchanged; 21.3.4.2 specifies the returned count but not that destination value.

Celox execution model ​

These choices belong to Celox's API, not to SystemVerilog; they decide which designs need the timed Simulation API and what the host can observe.

  • Simulator runs no processes. Constant initialization applies to both APIs. final procedures, initial blocks that read design state or call system tasks, processes with timing controls, and always blocks whose sensitivity list is neither @* nor exactly the variables the statement reads run as processes and need Simulation. Building a Simulator for such a design fails with SimulatorErrorKind::ProcessRequiresSimulation, naming the first process and its source location. An always whose list (or part-selects) covers exactly what the statement reads, with no timing control, nonblocking assignment, subroutine or system task call, self-read, or repeated store, simulates like always @* in both APIs; so does a flip-flop-shaped edge-sensitive always. Simulator::tick drives the rising edge of its event only; a Simulation runs every edge. A Simulator call is one time slot for $sampled and deferred assertions, and $time returns 0.
  • Host clocks. Simulation::add_clock and Simulation::schedule move an event signal: a clock or asynchronous reset of an edge-sensitive always, or a one-bit input of a top-level module that a process waits for. A process waits for the input its event control names (@(posedge clk), @(clk)) or its wait condition reads: in the top module itself, by a hierarchical name, or through port connections and continuous assignments that copy the whole signal unchanged. For any other signal schedule returns NotAnEvent and add_clock does nothing: an input read only as data, an iff condition, a multi-bit input, and the operands of an event expression such as @(posedge (clk & en)) are driven with modify between the runs. With several top-level modules, named_events() names the events of each top from it (hdl_top.clk), and add_clock_by_id and schedule_by_id move them. An event signal cannot be forced from the host: force_signals rejects a waited input as it rejects a clock. A clock on a waited input that another event is computed from (a gated clock, an inverted reset) is not compiled into the scheduler's time slots, so each of its edges is a step of the host.
  • Termination. final procedures run once on $finish, $fatal, or an explicit Simulation::finish(); an idle step() or the end of run_until() does not terminate the reusable Rust simulation. No scheduled events run afterwards, so a nonblocking assignment made directly in a final procedure never applies its queued update, and detached fork … join_none children declared in a final procedure are initialized but never start. $stop in an initial block suspends the simulation (is_stopped() is set and the next call continues); in an always process it is reported as RuntimeEvent::Stop, as $finish is RuntimeEvent::Finish. Batch hosts without an interactive mode, such as the VPI host, end the run at $stop. A checkpoint cannot be taken while suspended (CheckpointError::Stopped).
  • Reports. $info, $warning, $error, and $fatal — including the default $error of an assertion without a fail action — are delivered to the host as RuntimeEvent::Report with severity, message, file, line, scope, and simulation time. Only $error and $fatal fail a celox run; $fatal also ends the simulation.
  • Top-level modules. A simulation runs the top module it names. A design with several top-level modules (23.3.1), such as a testbench's hdl_top and hvl_top, runs them together when Rust's SimulatorBuilder::tops or a repeated celox run --top names them, each as an instance of its own name under $root, with its ports unconnected. Hierarchical names, %m, waveform scopes and the VPI and reflection hierarchy then start at a top (hdl_top.dut, $root.hdl_top.dut): each top is a root scope, as vpi_iterate(vpiModule, NULL) returns them. Signals are named from a top, as signal("hdl_top.clk") or child_signal(&[("hdl_top", 0)], "clk"), and so are forced and live signals. The design's tops are the selected modules: PreserveTopPorts keeps the ports of each, named_signals() names each top's signals from it (hdl_top.clk), named_hierarchies() gives each top's hierarchy, and named_hierarchy() is $root with the tops as its children. Several tops require SystemVerilog sources only and take no parameter overrides.
  • Observable names. Interfaces are expanded into the modules that use them: a member m of interface instance h becomes the signal h$m, an interface port at the top becomes ports such as bus$data, and a module with a generic interface port is copied per connected interface as M$I. Instance array elements are addressed by their declared index (dut.u[3], child_signal(&[("u", 3)], "y")). A package variable is named p::v and a compilation-unit variable $unit::v in sim.signal(…). Hierarchical names can address signals, including string variables, in both SystemVerilog code and the host API.
  • Heap and checkpoints. Strings, class objects, and containers live in a heap collected between time slots and after each tick; a string, class handle, process handle, or virtual interface is stored like a 32-bit integer. Core checkpoints (checkpoint() / restore()) preserve heap objects, fork children, process handles, random streams, pending strobe/monitor state, and deferred assertion queues. Portable state files are narrower: saving fails while any variable holds a class object, semaphore, mailbox, or exposed process handle, while a process waits for a named event or a current-slot trigger is still visible to triggered, while strobe output is pending, and for designs with file I/O, source VCD controls, or monitor tasks. Non-null class objects or dynamic containers, and nonempty string/object values in pending NBA writes, host writes, or event-wait baselines, likewise require a core checkpoint. Native images and serialized checkpoints from earlier heap or container layouts must be regenerated.
  • Loop progress. A run-time loop in always_ff that stops making progress reports a runtime error naming its loop variable.
  • Memory files. $readmemh and $readmemb read their file when they execute (21.4), never when the design is compiled, so compiled code, a JIT cache, and native images see the file as it is then. A load in an initial block that neither waits nor reads design state before it runs when each Simulator or Simulation instance is created, in both APIs; any other load runs at its statement, in always_ff at every activation and in always_comb whenever the block runs. A relative name is looked up in the working directory of the simulating process. The word-count warning and the errors of a load are RuntimeEvent::Reports; an error terminates the load, keeping the words loaded before it, and the simulation continues. An initial block that reads loaded words afterwards runs as a process. For the inferred-latch check of always_comb, a load assigns all the words it may load. An associative array is loaded when its indices are integral values of at most 64 bits and its elements packed values of at most 64 bits (21.4.1), always at its statement: each word creates or replaces the element of its address, which is the index's bit pattern (@fffffffe is the int index -2, as in Verilator). Without addresses in the call, a file address may name any index; an address or word that is no member of an enumerated index or element type is an error. An index that selects the array, as in banks[i++], must have no effect. Dynamic arrays and queues are not loaded.

Mixing Veryl and SystemVerilog ​

Mixed designs are a Celox feature, not part of the standard. Simulator::from_mixed_sources (or Simulation::from_sources(veryl).with_sv_sources(sv)) combines both source lists. Veryl instantiates an SV module with $sv::Module; SV refers to a Veryl module or interface by its emitted name (prj_Module, or Module with omit_project_prefix; the project is prj without a Veryl.toml).

DPI-C imports ​

A design can call C functions declared with import "DPI-C". celox run links the shared libraries named by --dpi-lib PATH (repeatable) and by dpi_libs in celox.toml. In the Rust API, DPI-C registration is a host API of the builder:

extern "C" fn c_add(x: i32, y: i32) -> i32 { x.wrapping_add(y) }

// SAFETY: `c_add` and the functions of libmodel.so have the signatures
// their imports declare.
let mut sim = unsafe {
    Simulator::from_sv_sources(vec![(source, Path::new("top.sv"))], "Top")
        .dpi_function("c_add", c_add as *const ())
        .dpi_library("libmodel.so")
}
.build()?;

Each import is linked by its C name at build time: dpi_function registrations are searched first, then dpi_library libraries in order; an unresolved name fails the build with a Dpi error. Both methods are unsafe, because Celox cannot check that a C function matches its import. allow_unlinked_dpi_for_elaboration() builds a design despite unresolved imports, for an elaboration that never runs it (the sv-tests runner's elaboration mode, which links no C code as other tools' does not): a call of such an import is a run-time error that names the import and says it was elaborated without its C body. It is off unless requested; simulation and every other build keep the error.

An output or inout argument is a pointer to its C type (a pointer to const char * for string). A string or packed array passed to the function is valid until it returns; a string it returns or writes to an output is copied when it returns. In two-state simulation, unknown bits a function writes to a logic argument read as zero. An always @* block that calls an import runs when what it reads changes (9.4.2.2) and no more often: a C function whose result changes without a change of its SystemVerilog arguments is not called again until one changes.

UVM's C library functions are provided by Celox and shadow any user implementation of the same name. The uvm_re_* functions use the Rust regex crate, whose syntax differs from POSIX extended regular expressions in rare constructs; uvm_dpi_get_next_arg_c returns celox followed by the plusargs and uvm_dpi_get_tool_name_c returns Celox. The uvm_hdl_* and uvm_polling_* functions return 0 or null, so UVM reports those facilities as unavailable. UVM 1.2's uvm_re_match, uvm_glob_to_re, uvm_dump_re_cache, uvm_dpi_regcomp, uvm_dpi_regexec, and uvm_dpi_regfree are provided too. Their reports (UVM/DPI/REGEX_INV, UVM/DPI/REGEX_MAX, UVM/DPI/REGCOMP, and the cache message) go through the function the UVM package exports for them, m__uvm_report_dpi, as UVM's C library makes them, so they count as UVM reports; the text after invalid glob or regular expression is the regex crate's reason, not regerror's.

SystemVerilog emitted by Veryl ​

The Veryl conformance suite also runs against the SystemVerilog that Veryl emits. The cases that remain excluded are:

  • Veryl emits invalid SystemVerilog for an array literal that mixes positional items with default: ('{a, default: b}).
  • Designs that opt into Veryl function calls with output arguments or side effects in always_ff have no SystemVerilog equivalent and are not emitted.
  • Testbench modules (initial blocks with clocking and $finish scheduling, hierarchical assignments) are not emitted as simulatable SystemVerilog modules.
