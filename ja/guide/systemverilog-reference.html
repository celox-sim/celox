SystemVerilog の対応範囲と逸脱事項 ​

導入と最初のシミュレーションは SystemVerilog サポートから始めてください。

前提: IEEE 1800-2023 ​

Celox は IEEE Std 1800™-2023 が規定する SystemVerilog を実装します。 このページは標準をなぞらず、標準との差分だけを次の5つに分類してまとめます。

  1. 未対応の機能 — 未実装でコンパイル時に拒否される構文や節。
  2. 部分対応の機能 — 特定の部分集合を実装している機能。各項目で対応と未対応を並べて示します。
  3. 個別制約 — 全体としては標準に従う機能における、個別のエッジケース制約。
  4. 意図的な逸脱 — 標準準拠コードに影響する逸脱と標準外コードの許容に分けて記載します。
  5. 処理系定義の選択と Celox の実行モデル — 標準が処理系に委ねる選択、および Rust の Simulator / Simulation の分離・ホストクロック・複数トップモジュール・チェックポイント・メモリファイル・言語混在・DPI-C 登録など Celox 固有の API。

適合保証の範囲: 標準準拠コードと標準外コード ​

  • 標準準拠コード: このページに記載のない未対応項目や制限・逸脱に該当しない限り、有効な IEEE 1800-2023 コードは標準どおりに実行されます（未実装機能は黙って誤動作させず、構文名と追跡 issue 番号 — 個別 issue が無い場合はフロントエンドのロードマップ #88 — を含む Unsupported エラーを返します）。記載のない差異が見つかった場合は不具合として issue を登録してください。
  • 標準外コード（既定モードと strict モード）: 標準外コードの受理は標準コードの誤動作とは重要度が異なるため、既定モードでは実用上の互換性緩和を警告付きでいくつか受理します（標準外コードの許容・[diagnostics]参照）。strict モード（strict = true / --strict / .strict(true)）ではこれらの互換診断がエラーになり、下記に明記した意図的な拡張を除いて strict モードで IEEE 1800-2023 外のコードを受け入れてしまう場合は不具合です。issue を登録してください。

測定した適合状況は検証結果のページで公開しています。

未対応の機能 ​

以下の構文や節は未実装であり、コンパイル時に拒否します（下記 covergroup の宣言のみの例外を除きます）。

  • 検証・設計構造ブロック: bind、checker、config、covergroup（クラス内でどこからも構築されない covergroup の宣言のみ受理。構築またはメソッド呼び出しは拒否）、clocking ブロックと clocking drive、ユーザー定義プリミティブ（UDP）、specify ブロック。
  • ポート形式: ref ポート（#427）。
  • union と配列・コンテナの混在型: tagged union、unpacked union、packed union の代入パターン、chandle の固定長 unpacked 配列（chandle a[4]、typedef 経由を含む）、動的コンテナの固定長 unpacked 配列（int a[2][$]、typedef 経由を含む）、固定長 unpacked 配列を要素とする動的コンテナ（int a[][2]）。
  • 制御フロー: disable fork 以外の disable 文。宣言初期化子、final、always_comb、always_ff 内の fork（これらの文脈にはスケジューラ用のプロセス基盤がありません）。
  • 時刻・システムタスク: wait_order、および未実装の IEEE 1800-2023 / Annex D システムタスク・関数。Celox は標準が定義する全タスク・関数名を認識しており、未対応のものは未使用パラメータや関数本体に書かれた場合も含め名前付きで報告します（例: $get_coverage）。

個別制約 ​

全体としては標準に従う機能における、個別の制約は次のとおりです。

  • デザイン構造:
    • module m({a, b}, c[3:0], .p(d)) のような non-ANSI ポート式（#1953）。ポート名のヘッダと本体宣言による素の non-ANSI ポートは対応します。
    • 非定数の ANSI input ポート既定値（23.2.2.4）、input 以外のポートの既定値、および unpacked 構造体ポートの既定値（定数のスカラ/単一 input ポート既定値は対応。定数の unpacked 配列 input ポート既定値は unpacked_port_default で警告し strict モードで拒否）。
    • generate ブロック内インスタンスのポート接続が宣言する暗黙ネット（6.10）: これを読む入力接続は拒否し、出力だけが駆動するものはブロックではなくモジュールのネットになります。
    • 多次元のインスタンス配列、負の下限を持つインスタンス配列、または4,095要素を超えるインスタンス配列。
    • package ネット（#1146）。package 変数はクロックやリセットにできません。
    • ワイルドカード import（26.3）: モジュール・interface・program・package スコープ、generate ブロック、手続きブロックは、参照位置ごとではなく本体全体で名前を1度だけ束縛します（export p::x; は package 内で束縛）。1つの束縛対象内で参照位置により異なる宣言を指す場合は拒否します。また、ブロック自身のワイルドカード import を通じて package 変数を読むブロックローカル初期化子も拒否します（#4350）。
    • $unit 変数を宣言できるソースファイルは1つだけです。
  • 型と式:
    • enum の packed 配列の要素に対する enum メソッド（first、next など）（#2417）。
    • ベクタ範囲外に出る定数部分選択の読み取り、および配列要素や内側 packed 次元の宣言範囲を出る定数部分選択の書き込み（#88）。素の packed ベクタへの一部範囲外定数書き込み（例: logic [7:0] q への q[9:6] = v で範囲内の q[7:6] のみに書く）と全ての実行時選択は標準に従います。
    • packed 構造体のメンバである構造体の packed 配列における、要素メンバへの実行時部分選択および要素選択（s.regs[i].q[j +: 4] など）。
    • パラメータ式中の縮約演算子（#456）。
    • 型演算子（6.23）: 型参照と値の比較、型に対する case の範囲項目、ポートを読む式や generate ブロック内の式への type(...) 適用。
    • $typename （20.6.1）: 一意な綴りを持たない型に対して処理系生成名を作らず拒否します。匿名 enum・構造体・union、soft/tagged union、unpacked 配列メンバを持つ unpacked 構造体、enum や符号付き typedef の packed 配列、整数でない値パラメータを持つクラス、$typename(a + b) のような名前やデータ型でない被演算子が該当します。20.6.1 に規則のない virtual interface 型は宣言どおり出力します（virtual bus_if、virtual bus_if.mp、virtual bus_if#(8, 4)）。
    • 展開時定数としての集約型パラメータ: unpacked 配列型のパラメータは開始時から値を持ちます。1次元配列パラメータの要素（および要素型が符号付き名前付き型の packed 配列でない限りその packed 次元の選択）が展開時定数になるのは、要素が127ビット以下かつ X/Z 無しの packed 整数で配列要素数が4,096以下の場合のみです。packed 構造体パラメータのメンバは127ビット超または X/Z を含まない限り展開時定数です。配列全体および上記以外の要素・メンバは展開時に必要な定数としては使えません。
  • プロセスとサブルーチン:
    • always_comb（#453）および always_latch（#431）内のノンブロッキング代入。ブロッキング代入を使ってください。
    • static 引数を持つ package および $unit の時間付き task。
    • 組み込み process クラスの構築・継承。関数からの自スレッド停止や await() 呼び出し。
    • ループ: 手続きループの展開は最大10,000回。実行時に回数が決まる組み合わせループは数え上げ for のみ。1モジュールあたりの loop-generate 展開総数が1,000,000回を超えた場合、ビット複合代入による genvar 更新（#455）、および generate 中の再帰的定数関数展開は拒否します。
    • final 手続き : タイミング制御、ユーザー task 呼び出し（関数経由を含む）、戻った後にイベントをスケジュールする関数（13.4.4）は拒否します。final 内で宣言した切り離された fork … join_none の子は初期化されますが開始しません（実行モデルも参照）。
    • 名前付きサブルーチン引数: 選択添字に手続き的副作用のある呼び出し。受け手やオブジェクトを読む先行引数に副作用がある場合の、always_comb や assign 内で受け手を使うメソッド既定値。

意図的な逸脱 ​

標準準拠コードに影響する逸脱 ​

有効な IEEE 1800-2023 コードを受理しつつ、標準と意図的に異なる挙動をとる項目です。移植性が必要なコードはこれらに依存しないでください。

  • program の継続代入は Reactive region で実行しません。 program 内の 継続代入はデザインの組み合わせ論理と評価し、program が書くデザイン論理は reactive region セットの実行中に安定します。そのため #0 の後に再開した program は新しい値を読みます。IEEE 1800-2023 4.5 では reactive region セットが 空になるまで評価しません。Icarus、Verilator、xezim も Celox と同じです。
  • モジュール跨ぎおよび virtual interface 経由で呼ぶ interface サブルーチンの記憶域。 複数モジュールの interface ポート経由で呼ぶ static な関数・task の static 変数、 および中断し得る task の static 仮引数は、interface インスタンスごとではなく 呼び出し側モジュールごとに保持します（13.3.2、13.4.2、#3739）。 インスタンス自身経由と単一モジュールポート経由の呼び出しは1つを共有します。 同様に、virtual interface 経由で呼ぶ interface の task・関数（vif.drive(req)、25.9）は ハンドルが指すインスタンスに対して実行しますが、static 変数は呼び出しを行うスコープごとに保持し、 仮引数は static なサブルーチンでも呼び出しごとに持ちます。
  • 手続き的 assign における間接書き込みの上書きタイミング。 手続き的 assign が 有効な間、通常の代入文以外による変数への書き込み（output 引数、連結先、遅延 NBA、 他モジュールの階層名）は抑止ではなくそのタイムステップ内で上書きされるため、 変数を待つプロセスが書き込まれた値を観測する場合があります。
  • 実行時書式の %p は文字列以外の値を簡略化します。 %p 変換がコンパイル時リテラルではなく 実行時に評価される書式文字列から来る場合、Celox は string を引用符付きで、それ以外の値を %0d として出力します。
  • カバレッジは報告しません。 即時 cover は pass 文を実行しますが、 カバレッジカウンタやレポートは公開しません。
  • program 外の $exit は警告します。 program スレッド以外からの $exit は 24.7 どおり無視しますが、Celox はコンパイル警告（[diagnostics] の exit_outside_program）も出します（未使用関数の宣言内呼び出しも含みます）。
  • UVM の DPI 関数は組み込みです。 UVM の src/dpi の C 名での import は ユーザー C 関数ではなく Celox の実装に束縛します。DPI-C importsを参照してください。
  • オプトインの互換モード。 [compatibility] の legacy_empty_reductions や shared_always_temporary などのオプションは、 既定では IEEE 1800-2023 準拠の挙動を保ち、明示的に有効化したときだけ逸脱します。

標準外コードの許容 ​

Celox が意図的に受理している標準外構文および互換拡張です。移植性が必要なコードはこれらに依存しないでください。

既定で警告、strict モード（strict = true / --strict / .strict(true)）で拒否:

  • 初期化付きローカル変数での static キーワード欠落を許容（6.21）。 IEEE 1800-2023 6.21 は初期化値を持つ static 変数の宣言に明示的な static を要求します。 Celox は定数初期化子ではどの手続きでも、実行時初期化子では initial のような 1度だけ実行する手続きでキーワード無しの宣言も受け付け、implicit_static_initializer 警告 （既定 warn、strict mode で error）を出します。always 内の実行時初期化子に static も automatic も無い場合は拒否します。
  • 時間尺度の有無が混在する場合の既定値フォールバック（3.14.2.3）。 一部の設計要素だけ時間単位・精度（宣言・継承・`timescale）を持ち他が持たない場合に エラーとせず、mixed_timescale 警告（strict mode で error）を出して該当要素に 1 ns / 1 ps を割り当てます。
  • その他の既定警告な互換診断。 重複モジュール宣言（duplicate_module）、 固定長 interface 配列への $size（interface_array_query）、interface 配列への bus.WIDTH 省略記法（interface_array_parameter）、定数 unpacked 配列の input ポート既定値 （unpacked_port_default、23.2.2.4）、always_ff と他エッジプロセスによる メモリ共有（multiple_always_ff_drivers）は、既定で警告を出し strict mode で拒否します。 詳細は [diagnostics]（および inferred_latch）を参照してください。

strict モードでも受理する意図的な拡張:

  • 固定長 unpacked 配列への packed 値と一括充填の代入（7.6）。 配列全体とちょうど同じ幅の packed 値をビットごとに代入すること、および '0 のような unbased unsized リテラルで全要素を埋めることを受理します。それ以外の幅の値、real、string は拒否します。
  • 変数の選択や unpacked 配列要素への手続き的 force（10.6.2）。 標準がベクタネットに限定している force を、変数の定数ビット/部分選択・メンバ、および packed 整数型固定長 unpacked 配列の定数添字要素（または定数選択・メンバ）へ拡張しています （条件により forced_array 警告を出します）。
  • $psprintf を $sformatf として受理。 ベンダー拡張の $psprintf を $sformatf（21.3.3）として受理し、診断では $sformatf と表示します。

処理系定義・順序未規定の挙動 ​

IEEE 1800-2023 が処理系に委ねる点、順序を指定しない点、非決定的とする点について、 Celox は次のように選びます。移植可能なコードはこれらに依存しないでください。

定数の幅 ​

IEEE 1800-2023 は、ベクタの幅の上限を 65,536 ビット以上の範囲で処理系に委ねます（6.9.1、7.4.1）。 パラメータ、それを作る連結、その部分選択などの定数値は最大 1,048,576 ビットまで許容します。 複製、ビットごとに組み立てる定数、定数関数呼び出し内の値は最大 65,536 ビットです。 これを超える定数は構築前に拒否します。

イベント実行順序 ​

Clause 4.7 がどちらの順序も許すケースで、Celox は決定的です。

  • 継続代入・組み合わせプロセス・イベント式が時間を持つプロセスの書き込みを見るのは、 そのプロセスがタイミング制御に達したとき、または終わったときです。 b = 1; a = 1; の後では a ^ b は変化しておらず、パルス a = 1; a = 0; は @(a) を起こしますが @(a ^ b) は起こしません。式待ちに見せたい場合は 書き込みの間に #0 を置いてください。fork 共有自動ローカル上の複合待ちは、 対応するブロッキング代入と文呼び出しのコピーアウトを個別に観測します。
  • 待ち側は、always_comb・always @*・エッジ駆動プロセスの1回の評価が書く 全ての値を見ます。後の書き込みで上書きされる値も含みます（4.3、9.4.2）。 子インスタンスの出力ポート（継続代入、23.3.3）越しでは、親の待ち側は 安定した値だけを見ます。
  • expr iff condition 項目（9.4.2.3）は、両者が変数の場合 expr の各書き込みで 判定します。1プロセス内では clk = 1; en = 0; はイベントとなり、 en = 0; clk = 1; はなりません。どちらかが一般式やネットの場合、または expr をフリップフロップ領域が書く場合 （#1830）は、発生検出時 （組み合わせ論理の安定後）に判定します。
  • クラスプロパティを読む wait 条件は、それが読むプロパティの全てのストアの後に 再確認します。どのハンドル越しでも、各 randomize() の後でもです。別オブジェクトの 同プロパティや、すでに保持している値のストアでも再確認するため、最小限より 頻繁に確認することがあります（9.4.3）。
  • 非同期リセットがある場合、$past の履歴ティックはクロックがタイムスロット前の レベルを離れた実行です。スロット内で同レベルに戻るクロックは履歴を進めません。 1タイムステップ内の複数クロック遷移は並行アサーションでは未定義です（16.5）。

時刻と精度 ​

  • 処理系既定の時間尺度は 1 ns / 1 ps です。Simulation はデザイン全体の 時間精度（3.14.3）で数えます。既定では 1 ps なので、時間尺度の無い デザインでは %t はピコ秒を報告します。
  • $timeformat（20.4.3）は以降のすべての出力および $sformatf における %t 変換の 単位・小数点以下桁数・接尾辞・最小フィールド幅を設定します。丸めは四捨五入（0から離れる方向）で、 %0t などの幅指定は最小フィールド幅を置き換えます。接尾辞は NUL 文字を含む文字列リテラルです。 これを呼ぶ always_comb・always_latch・always @*（サブルーチン経由を含む）はプロセスとして実行し、 時刻 0 で1度（always @* を除く）と読み取り対象の変化ごとに動きます。 実行時に単位番号が 2〜-15 の範囲外になるか精度・幅が負になると実行時エラーで終了し、 定数の場合は解析エラーになります。小数点以下桁数とパディング幅の上限は 4,096 です。
  • コンパイル単位（$unit）で宣言されたクラスやサブルーチンは、コンパイル単位の 時間単位と時間精度を使用します。`timescale 指令はこれらを設定しないため（3.14.2.3）、 $unit 内で timeunit/timeprecision を宣言しない限り既定の 1 ns / 1 ps になります （Verilator は最後の `timescale を適用します）。移植可能なコードでは $unit に timeunit を宣言してください。全体の時間精度より細かい精度は整数ステップへ丸められます。
  • final 手続きは決定的ですが順序未規定の順に逐次実行します。コンストラクタや 関数を呼ぶ package・モジュール変数初期化子の相対順序も未規定です（6.8、10.5）。 依存しないでください。

乱数 ​

  • $urandom は決定的な32ビット線形合同生成器を使います（18.13.1、18.14）。 既定シードと系列は処理系定義で、他シミュレータと一致する必要はありません。 $random と $dist_* は Annex N に従うため、同附属書の他実装と一致します。 process およびクラスオブジェクトの乱数状態文字列（get_randstate、18.13.4）は 不透明で Celox 固有です。set_randstate（18.13.5）は get_randstate が返した文字列だけを 受け付け、それ以外ではシミュレーションをエラー終了します。
  • 組み合わせ手続きでは、プロセス活性化時に乱数を引きます。入力不変の 再評価ではストリームは進みません。
  • 制約付き randomize() はオブジェクトのシードで充足代入を探索し、選択した 全プロパティをまとめて更新します。一様分布は保証しません （#2187）。 不充足が証明された場合は 0 を返し、プロパティを保持し、post フックを 省略します（18.6.3）。資源枯渇は実行時エラーです。
  • soft 制約（18.5.13）は優先度の高い順から試み（18.5.13.1）、ハード制約と 先行して維持した soft 制約と両立すれば維持し、そうでなければ破棄します。 disable soft はその変数を名指す下位の soft 制約を破棄します（18.5.13.2）。 各段階の探索はシードを保持するため選択は再現可能です。soft dist は重み非ゼロの項目に 被演算子を制約し、維持されている間はハードな dist と同様に重みで選択を偏らせ（18.5.3）、 破棄されると影響を与えません。
  • 4値 rand プロパティは2値の結果をとります。4値状態プロパティ、4値型の制約内関数戻り値、 インライン制約や std::randomize() with の4値呼び出し側入力に含まれる X/Z ビットは各演算の 4値規則（11.4）に従います。X/Z が制約やガードの真偽を決める場合は実行時エラー（18.3）となり、 マスク・選択・既知 0 が決める && などで真偽を決めない場合はそのまま値を使います （そうしたガードは求解前に評価します、18.5.13）。真偽がランダム変数にも依存する場合は、 見つかった解が到達するかどうかを決めます。
  • solve before（18.5.9）は解の集合を変えず、探索の選択順序にも影響しません。循環順序の診断も行いません。
  • 制約が呼ぶ関数（18.5.11）は通常の呼び出し（オブジェクトのクラスによるオーバーライドを含む）として実行します。 引数内のランダム変数がそれらだけを含む制約で解かれた後に呼ばれ、戻り値は他の制約に対する状態入力となるため、 他の制約により解無しになることがあります。引数でないランダム変数を関数が読む場合は呼び出し前の値を読みます。
  • randsequence（18.17）: 複数の生成規則は重み（省略時は 1）に従ってスレッドの乱数生成器から1つを選びます（18.14.2）。 rand join は同じ乱数生成器を使って項目をランダムに織り交ぜます。18.17.5 は bias に数式を定めていないため、 Celox は bias を1度評価し、各ステップで確率 |2 × bias − 1| で残項目が最少（bias < 0.5）または最多（bias > 0.5）の規則を進め、 それ以外は残項目のある任意の規則を等確率で進めます（0.5 は偏り無し、0.0 と 1.0 はそれぞれ最短・最長を常に優先）。
  • 配列の shuffle は呼び出しプロセスの乱数ストリームから引きます。

ホスト依存の結果 ​

  • $ferror のコードと文言はホスト依存です。Celox は失敗した $fopen の 詳細を FD 0 でも公開します。
  • $system は C の system() の値を返します。ホストの終了状態エンコーディングを 含みます（20.17.1）。相対ファイルパスはホストプロセスの作業ディレクトリ基準です。
  • 読み込みバイトが無い $fgets は送信先を変更しません。21.3.4.2 は返却する 件数を規定しますが、その場合の送信先の値は規定しません。

Celox の実行モデル ​

以下は SystemVerilog ではなく Celox API の選択です。どのデザインに時間付き Simulation API が必要か、ホストが何を観測できるかを決めます。

  • Simulator はプロセスを実行しません。 定数初期化は両 API に適用されます。 final 手続き、デザイン状態を読む・システムタスクを呼ぶ initial ブロック、 タイミング制御を持つプロセス、@* でも文が読む変数そのものでもない センシティビティリストを持つ always はプロセスとして実行するため Simulation が必要です。Simulator で構築すると SimulatorErrorKind::ProcessRequiresSimulation で失敗し、最初のプロセスと ソース位置を示します。リスト（部分選択を含む）が文の読み対象をちょうど覆い、 タイミング制御・ノンブロッキング代入・サブルーチンやシステムタスク呼び出し・ 自己読み・重複ストアを持たない always は、両 API で always @* のように 振る舞います。フリップフロップ形のエッジ駆動 always も同様です。 Simulator::tick は自イベントの立ち上がりだけを駆動します。Simulation は 全エッジを実行します。Simulator の1呼び出しは $sampled と遅延アサーションに ついて1タイムスロットであり、$time は 0 を返します。
  • ホストクロック。 Simulation::add_clock と Simulation::schedule は イベント信号（エッジ駆動 always のクロックや非同期リセット、またはプロセスが待つ トップモジュールの1ビット入力）を動かします。プロセスが待つのは、イベント制御が名指す入力 （@(posedge clk)、@(clk)）または wait 条件が読む入力で、トップモジュール自身、階層名、 または信号全体をそのままコピーするポート接続・継続代入経由のものに限られます。 それ以外の信号（データとしてのみ読まれる入力、iff 条件、複数ビット入力、@(posedge (clk & en)) の ようなイベント式の被演算子など）に対しては、schedule は NotAnEvent を返し、add_clock は何もしません。 これらは実行の間に modify で駆動します。複数トップモジュール時は named_events() が 各トップからイベント名を返し（hdl_top.clk）、add_clock_by_id / schedule_by_id で駆動できます。 イベント信号はホストから force できません（force_signals は待機される入力もクロックと同様に拒否します）。 別イベントの計算元となる待機入力上のクロック（ゲーテッドクロック、反転リセットなど）はスケジューラの タイムスロットにコンパイルされないため、各エッジがホストの1ステップになります。
  • 終了。 final 手続きは $finish・$fatal・明示的な Simulation::finish() で1度実行します。空の step() や run_until() の 終端では、再利用可能な Rust シミュレーションは終了しません。その後は スケジュール済みイベントは実行しないため、final 内で直接行った ノンブロッキング代入のキュー更新は適用されず、final 内で宣言した切り離された fork … join_none の子も初期化されますが開始しません。initial 内の $stop は シミュレーションを停止します（is_stopped() が立ち、次回呼び出しで継続）。 always 内では RuntimeEvent::Stop として、$finish は RuntimeEvent::Finish として報告します。VPI ホストなど対話モードの無い バッチホストは $stop で実行を終えます。停止中はチェックポイントを取れません （CheckpointError::Stopped）。
  • 報告。 $info・$warning・$error・$fatal（失敗アクション無し アサーションの既定 $error を含む）は、重大度・メッセージ・ファイル・行・ スコープ・シミュレーション時刻を持つ RuntimeEvent::Report として ホストへ届きます。celox 実行を失敗とするのは $error と $fatal だけで、 $fatal はシミュレーションも終えます。
  • トップレベルモジュール。 シミュレーションは指定されたトップモジュールを実行します。 テストベンチの hdl_top と hvl_top のような複数トップモジュール（23.3.1）を持つデザインは、 Rust の SimulatorBuilder::tops または複数回の celox run --top で指定すると、 $root 配下にそれぞれの名前のインスタンス（ポート未接続）として同時に実行します。 階層名、%m、波形スコープ、VPI/リフレクション階層は各トップから始まり（hdl_top.dut、$root.hdl_top.dut）、 各トップが vpi_iterate(vpiModule, NULL) で返るルートスコープになります。 信号・force 対象・live 信号も各トップから指定します（signal("hdl_top.clk") や child_signal(&[("hdl_top", 0)], "clk")）。PreserveTopPorts は各トップのポートを保持し、 named_signals() は各トップからの信号名（hdl_top.clk）、named_hierarchies() は各トップの階層、 named_hierarchy() はトップ群を子とする $root を返します。複数トップは SystemVerilog ソースのみに対応し、 パラメータ上書きは取れません。
  • 観測できる名前。 interface は使用モジュールへ展開します。interface インスタンス h のメンバ m は信号 h$m となり、トップの interface ポートは bus$data のようなポートとなり、汎用 interface ポートを持つモジュールは 接続 interface ごとに M$I として複製します。インスタンス配列要素は宣言添字で 指定します（dut.u[3]、child_signal(&[("u", 3)], "y")）。package 変数は p::v、コンパイル単位変数は $unit::v と sim.signal(…) で名指します。 階層名は SystemVerilog コードとホスト API の双方で、string 変数を含む信号を指定できます。
  • ヒープとチェックポイント。 文字列・クラスオブジェクト・コンテナは、 タイムスロット間と各 tick 後に回収するヒープにあります。string・ クラスハンドル・process ハンドル・virtual interface は32ビット整数のように 保持します。コアチェックポイント（checkpoint() / restore()）は ヒープオブジェクト、fork の子、process ハンドル、乱数ストリーム、保留中 strobe/monitor 状態、遅延アサーションキューを保持します。移植用状態ファイルは 狭く、変数がクラスオブジェクト・semaphore・mailbox・公開済み process ハンドルを持つ間、プロセスが named event を待つ間や現在のトリガが triggered に見える間、strobe 出力が保留中の間、ファイル I/O・ソース VCD 制御・ monitor タスクを持つデザインでは保存に失敗します。非 null のクラスオブジェクトや 動的コンテナ、保留 NBA・ホスト書き込み・イベント待ち基準内の空でない string/オブジェクト値もコアチェックポイントを必要とします。旧ヒープ・ コンテナレイアウトのネイティブイメージと直列化チェックポイントは再生成が必要です。
  • ループの進行。 進行しなくなった always_ff 内実行時ループは、 ループ変数名を含む実行時エラーを報告します。
  • メモリファイル。 $readmemh と $readmemb は 実行された時にファイルを読み（21.4）、デザインのコンパイル時には読みません。そのため コンパイル済みコード、JIT キャッシュ、ネイティブイメージもその時点のファイルを読みます。 待機もデザイン状態の読み出しもその前に行わない initial ブロックの読み込みは、 Simulator と Simulation のどちらでもインスタンスを作るたびに実行します。それ以外の 読み込みは文の位置で実行し、always_ff では活性化のたびに、always_comb では ブロックが実行されるたびに読みます。相対パスはシミュレーションを実行するプロセスの 作業ディレクトリから探します。ワード数不一致の警告と読み込みのエラーは RuntimeEvent::Report になります。エラーはそれ以前に読んだワードを残して読み込みを 打ち切り、シミュレーションは続行します。読み込んだワードをその後で読む initial ブロックはプロセスとして実行します。always_comb のラッチ推論の検査では、 読み込みは読み込み得るワードをすべて代入したものとみなします。 連想配列は、インデックスが 64 ビット以下の整数値で要素が 64 ビット以下の packed 値の ときに読み込みます（21.4.1）。常に文の位置で実行し、各ワードはそのアドレスの要素を 作成または置き換えます。アドレスはインデックスのビットパターンです（Verilator と同じく @fffffffe は int のインデックス -2）。呼び出しにアドレスが無い場合、ファイルの アドレスは任意のインデックスを指せます。列挙型のインデックスまたは要素のメンバーでない アドレスやワードはエラーです。banks[i++] のように配列を選択するインデックスは副作用を 持ってはいけません。動的配列とキューには読み込みません。

Veryl と SystemVerilog の混在 ​

DPI-C imports ​

import "DPI-C" で宣言した C 関数を呼べます。celox run は --dpi-lib PATH（繰り返し可）と celox.toml の dpi_libs で指定した 共有ライブラリをリンクします。Rust API では、DPI-C 登録はビルダーのホスト API です。

rust
extern "C" fn c_add(x: i32, y: i32) -> i32 { x.wrapping_add(y) }

// SAFETY: `c_add` and the functions of libmodel.so have the signatures
// their imports declare.
let mut sim = unsafe {
    Simulator::from_sv_sources(vec![(source, Path::new("top.sv"))], "Top")
        .dpi_function("c_add", c_add as *const ())
        .dpi_library("libmodel.so")
}
.build()?;

各 import は構築時に C 名でリンクします。dpi_function 登録を最初に探し、 次に dpi_library のライブラリを順に探します。解決できない名前は Dpi エラーで 構築に失敗します。C 関数と import の一致を Celox は検証できないため、両方とも unsafe です。allow_unlinked_dpi_for_elaboration() は、実行しない elaboration のために （他のツールと同様に C コードをリンクしない sv-tests ランナーの elaboration モード）、 未解決の import があっても設計を構築します。そうした import の呼び出しは、import 名と C 本体なしで elaboration されたことを示す実行時エラーになります。 明示的に要求しない限り無効で、シミュレーションや他の構築ではエラーのままです。

output・inout 引数はその C 型へのポインタ（string では const char * へのポインタ）です。 関数に渡した string と packed 配列は関数が戻るまで有効で、関数が返す、または output に書く string は戻った時点でコピーします。 2値シミュレーションでは、関数が logic 引数に書いた不定ビットは 0 として読みます。 import を呼ぶ always @* ブロックは読み取り対象の変化時にのみ実行し（9.4.2.2）、 SystemVerilog 側の引数が変わらなければ C 関数の結果が変わっても再呼び出しされません。

UVM の C ライブラリ関数は Celox が提供し、同名のユーザー実装を覆い隠します。 uvm_re_* は Rust の regex クレートを使うため、まれな構文で POSIX 拡張正規表現と異なります。 uvm_dpi_get_next_arg_c は celox と plusargs を返し、uvm_dpi_get_tool_name_c は Celox を返します。 uvm_hdl_* と uvm_polling_* は 0 または null を返すため、UVM はそれらの機能を利用不可と報告します。 UVM 1.2 の uvm_re_match・uvm_glob_to_re・uvm_dump_re_cache・uvm_dpi_regcomp・uvm_dpi_regexec・uvm_dpi_regfree も提供します。 これらのレポート（UVM/DPI/REGEX_INV・UVM/DPI/REGEX_MAX・UVM/DPI/REGCOMP とキャッシュメッセージ）は UVM の C ライブラリと同じく UVM パッケージがエクスポートする m__uvm_report_dpi を通して出すため UVM のレポートとして数えられ、 invalid glob or regular expression の後の理由は regerror ではなく regex クレートのものです。

Veryl が出力する SystemVerilog ​

Veryl の適合性スイートは Veryl が出力した SystemVerilog に対しても実行します。 残る対象外は次のとおりです。

  • 位置項目と default: を混ぜた配列リテラル（'{a, default: b}）に対して Veryl が不正な SystemVerilog を出力します。
  • always_ff 内で出力引数や副作用のある Veryl 関数呼び出しをオプトインした デザインには SystemVerilog での等価物が無く、出力しません。
  • テストベンチモジュール（クロックと $finish スケジューリングを持つ initial ブロック、階層代入）はシミュレート可能な SystemVerilog としては 出力しません。
