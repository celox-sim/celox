SystemVerilog サポート ​

Celox は、SystemVerilog で記述した同期 RTL を Rust API からシミュレートできます。 Cargo feature の systemverilog を有効にし、ソースファイルとトップモジュールを指定して使います。 TypeScript パッケージと Vite プラグインは、現時点では Veryl のみを読み込みます。

モジュール、メモリ、interface、2 値・4 値シミュレーションなど、SystemVerilog の一部に対応しています。 バックエンドとランタイムは Veryl と共通です。個々の構文の対応状況は 言語リファレンスで確認できます。

最初のモジュールを動かす ​

Rust プロジェクトで feature を有効にします。

toml
[dependencies]
celox = { version = "*", features = ["systemverilog"] }

Simulator::from_sv_sources にソース文字列とそのパスを渡し、トップモジュール名を指定します。

rust
use celox::Simulator;
use std::path::Path;

let source = r#"
    module Counter(input logic clk, input logic rst, output logic [7:0] q);
        always_ff @(posedge clk) q <= rst ? 8'd0 : q + 8'd1;
    endmodule
"#;
let mut sim = Simulator::from_sv_sources(
    vec![(source, Path::new("counter.sv"))],
    "Counter",
)
.build()?;

let clk = sim.event("clk");
let rst = sim.signal("rst");
let q = sim.signal("q");
sim.modify(|io| io.set(rst, 1u8))?;
sim.tick(clk)?; // カウンタをリセット。
sim.modify(|io| io.set(rst, 0u8))?;
sim.tick(clk)?; // 立ち上がりエッジを1回進める。
assert_eq!(sim.get(q), 1u8.into());

ファイルが複数ある場合は、同じリストに追加します。各ファイルは独立したコンパイル単位です。 トップには SystemVerilog のモジュール名を指定します。

デザインの動かし方を選ぶ ​

テストで行いたいことAPI
Rust から入力を設定し、論理を評価してクロックイベントを進めるSimulator::from_sv_sources
シミュレーション時刻を進め、タイミング制御を持つ initial / always プロセスを実行するSimulation::from_sv_sources
Veryl と SystemVerilog のソースを一緒に扱うSimulator::from_mixed_sources

Simulator::tick は指定イベントの立ち上がりエッジを駆動します。 Simulation は時刻を管理し、スケジュールされたエッジを実行します。 定数による初期化はどちらにも適用されます。デザインの状態を読む、またはシステムタスクを呼ぶ initial ブロック、タイミング制御を持つプロセス、@* でも 文が読む変数でもないセンシティビティリストを持つ always はプロセスとして実行するため Simulation が必要です。Simulator はプロセスを実行しないため、 このようなデザインでは SimulatorErrorKind::ProcessRequiresSimulation でビルドに失敗し、 最初のプロセスとそのソース位置を示します。Veryl と混在する階層では Simulation::from_sources(veryl).with_sv_sources(sv) で Simulation を作成します。

X/Z を扱う場合は builder に .four_state(true) を指定します。 状態モデルは 4 値シミュレーション、時刻、$stop、メモリの読み込みなどは 実行時のリファレンスで説明しています。

サポートしているもの ​

主な対応範囲は次のとおりです。

領域例
デザイン構造モジュール階層、パラメータ、generate、package、interface と modport
データpacked ベクタ、多次元 packed 配列、構造体、enum、unpacked メモリ
RTL のプロセスassign、always_comb、always @*、ブロッキング代入の always_latch、エッジで起動する always と always_ff
時間を持つプロセス#delay（#5ns などの時間リテラルを含む）、変数・エッジ・選択・式・@* に対する @(...)、wait (...)、ノンブロッキング代入、タイミング制御を持つ task 呼び出しを使う initial と always
演算と制御算術、部分選択、assignment pattern、分岐、ループ、関数
シミュレーション補助即時アサーションと遅延付き即時アサーション、表示タスク、$readmemh / $readmemb、時刻の取得、乱数

各領域には制約があります。デザインを移植する際は、 詳しい対応一覧でポート、型、文、システム関数を確認してください。

and、nand、or、nor、xor、xnor は、遅延・強度指定がなく、端子が1ビットの整数式なら対応しています（IEEE 1800-2023 28.4）。名前付き・名前なし、同一宣言での複数インスタンス、generate スコープを利用できます。

サポートしていないもの ​

デザインの変更が必要になりやすいのは、次の機能です。

  • 単純なクラスを超えるクラスを使う検証、単一サイクルBoolean部分集合を超える並行アサーション。
  • fork / join、ノンブロッキング代入内のイベント制御と定数でない遅延、 always_ff のイベント制御の iff（#452）。
  • ラッチ内のノンブロッキング代入、複数ドライバ、トライステートバス。always_comb の暗黙のラッチ推論は 共通の [diagnostics] 設定で inferred_latch = "warn" または "allow" を指定して許可します。
  • 非 ANSI モジュールポート、ワイルドカード .* 接続、遅延・強度指定やインスタンス配列を持つゲートプリミティブ、bind。
  • real、ポートや、整数以外・2 値と 4 値の混在・メンバ初期値を含む固定長配列の unpacked 構造体、interface の一部の機能。

制約の一覧に、より細かな条件と追跡 issue をまとめています。 未対応の構文は、構文名と追跡 issue を含む診断を返します。

Veryl と混在させる ​

どちらの言語もトップにでき、モジュール階層は双方向に言語境界を跨げます。 Simulator::from_mixed_sources に両言語のソースを渡します。 Veryl からは $sv::Module、SV からは prj_Module などの Veryl の出力名で参照します。

interface と input / output modport も言語間で接続できます。 名前の付け方、interface パラメータ、言語間の制約は Veryl と SystemVerilog の混在を参照してください。

DPI-C imports ​

sv-dpi を有効にすると、対応する C 関数を SV のクロックで起動するプロセスから呼び出せます。 関数や共有ライブラリは dpi_function / dpi_library で登録します。 C と SV の型を一致させる必要があるため、どちらも unsafe API です。 対応する型と呼び出し位置は DPI-C importsを参照してください。

個別の挙動を調べる ​

  • 初期化、スコープ、変数の寿命、メモリファイル
  • プロセス内のイベント待ちとレベル待ち
  • 時間単位、精度、時刻の取得
  • 乱数のシードと再現性

Veryl が出力する SystemVerilog ​

Veryl の適合性スイートは、Veryl が出力した SystemVerilog も検証します。 出力できないケースや言語間で意味が異なるケースは、残る対象外のケースを参照してください。
