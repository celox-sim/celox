並列シミュレーション ​

Celox は 1 つの設計を複数スレッドで評価できます。コンパイル時に、組み合わせ回路の 評価（settle）と各クロックイベントの順序回路更新を、スレッドごとの レーン に分割し、 レーンを並行実行します。結果は逐次シミュレーションと常に一致します。

スレッドの有効化 ​

rust
use celox::Simulator;

let mut sim = Simulator::builder(code, "Top")
    .threads(4)
    .build()?;
typescript
const sim = await Simulator.create(module, { threads: 4 });

threads は呼び出し元スレッドを含む数です。threads(4) ではワーカースレッドを 3 つ起動します。既定値の 1 では逐次カーネルのみをコンパイルします。

効果が出る場合 ​

1 サイクル内に独立した処理が多い設計で効果があります。たとえばデータパスの 多数のインスタンス、幅の広い複製ロジック、大きなレジスタ群などです。1 サイクル あたり数百ナノ秒程度の同期コストが固定でかかるため、1 サイクルの処理がおよそ 1 マイクロ秒以下の小さな設計は速くなりません。

Celox は次の 2 段階で、並列化によって遅くなることを防ぎます。

  1. コンパイル時: 見積もった高速化が同期コストを上回るフェーズだけを分割し、 そうでないフェーズは逐次コードのままにします。
  2. 実行時: 分割したフェーズは最初の数十回の呼び出しで逐次版と実測比較し、 速い方を使い続けます。比較は間隔を倍々に広げながら再実行されるため、 マシンが混雑していた時の判断も後で修正されます。

測定は通常のシミュレーションの一部として行われるため、結果は変わりません。 1 回の測定のコストは遅い方の実装を数十回実行する分だけです。

スレッド数の選び方 ​

  • 物理コア数以下にしてください。レーン間の待ち合わせはスピンで行うため、 SMT の兄弟スレッドやコアの過剰割り当ては全体を遅くします。
  • 最適化レベルと同様に、同じ入力とサイクル数で 実際のワークロード全体を測定してください。
  • スレッドを増やして効果があるのは、各レーンに 1 サイクルあたり十分な処理が 残っている間だけです。

並列化されるフェーズ ​

フェーズ分割
組み合わせ回路の評価（eval_comb）あり
1 つのクロック/リセットイベントの順序回路更新あり
同時に発火する複数クロックドメイン、カスケードクロック逐次
ネイティブの comb + FF 融合ティックループ分割フェーズの方が速い場合に置き換え

$display やアサーションなどのランタイムイベント、クロックイベントを発火しうる ストアの順序は、逐次シミュレーションとまったく同じに保たれます。

バックエンド ​

並列実行はネイティブの x86-64・AArch64 バックエンドと Cranelift で利用できます。 WebAssembly バックエンドとインタプリタは常に逐次実行です。外部インタフェース向けの ネイティブ force サポートを有効にした場合も逐次実行になります。

メモリ配置 ​

各レーンの状態は、キャッシュライン境界に揃えガードバイトで区切った専用の メモリセグメントに置かれます。そのため、設計上複数レーンが書くオブジェクト （たとえば同じ配列の別要素）を除き、レーン同士が同じキャッシュラインに書き込む ことはありません。設計の詳細は 並列実行 を 参照してください。

スケジューラーの可視化とデバッグ ​

次のコマンドで、ブラウザーで開ける単一 HTML と元の JSON を生成できます。

sh
cargo run --locked --release -p celox-bench --bin parallel-report -- \
  --output work/parallel-auto
cargo run --locked --release -p celox-bench --bin parallel-report -- \
  --always --output work/parallel-forced

出力先の report.html を開いてください。組み込み例は 16 個の独立した クロック付きデータパスです。通常設定と --always を比較すると、実際の 自動選択と、並列実行を強制した場合を確認できます。

  • Source partition: 配置候補・推定コストと依存グラフ。ノードを選ぶと、 個々の LogicPath、読み書きする信号、共有式による結合、配置制約を確認できます。
  • Memory dependencies: 最適化後の物理ビット範囲（StateBits）に基づく RAW/WAR/WAW、書き込み幅の拡大（バイト単位）、最終タスク間の依存関係を確認できます。
  • Execution: タスク本体と依存先ごとの待機時間、レーン間の重なり、 順序違反の検査結果を表示します。タスクを選ぶと SIR と信号名を確認できます。
  • Event inspector: 信号名などで検索し、SLT の式、FF の配置判断、逐次／並列の 実測中央値と選択結果まで追えます。

速度比はトレースを無効にした 6 ブロックの計測中央値です。詳細トレースには 計測負荷があり、タイムラインの重なりは CPU 上での同時稼働を保証しません。 組み込み例では各キャプチャ tick の後に全 16 出力を逐次版と照合します。 独自の設計は --source、--top、--clock、--set name=123、 --observe signal を指定できます。固定入力で指定イベントを繰り返すランナーなので、 任意のテストベンチやリセット手順を自動実行するものではありません。 詳細と制約は 英語ガイド を参照してください。

Veryl プロジェクトの実テストベンチも実行できます。

sh
cargo run --locked --release -p celox-bench --bin parallel-report -- \
  --project /path/to/heliodor --top test_soc_smp_linux_boot_4hart \
  --threads 4 --testbench-ticks 10000 --warmup 256 --capture 16 \
  --omit-sir --output work/heliodor-4core

このモードでは --warmup と --capture は tick 数ではなく、選択対象の 最外側のカーネル呼び出し回数です。内部の入れ子の選択は同じ採取区間に含めます。 --project はルート、子ディレクトリ、Veryl.toml のいずれも指定でき、 相対パスは発見したプロジェクトルートから解決します。 実際のリセット、メモリイメージ、initial の刺激を 使い、指定区間だけワーカーの詳細トレースを有効にします。逐次／並列の選択記録は 全区間で保存しますが、採取中の校正値にはトレースの負荷が含まれ得ます。 指定 tick で打ち切るため、Linux 起動完了や逐次版との同値性を保証するものではなく、 速度向上率も表示しません。--source を繰り返すと、プロジェクトルートからの 相対パスで対象ファイルを限定できます。

--omit-sir は巨大な展開済み SIR 文字列を省き、ソース式・配置候補・物理的な 読み書き範囲・実行時の待ちを保持します。各メモリ依存には代表的な衝突範囲を 1組示し、全読み書き範囲は footprint に残します。グラフは最大300ノードずつ 表示し、名前の絞り込みで残りを調べられます。RTL インスタンス別の割り当て表は パス数を数えており、CPU の hart とシミュレーターのレーン、実測時間を区別します。 テストベンチモードの --observe SIGNAL は終了時の値を16進数で保存します。 別のシミュレーターとの比較ではありません。入力刺激はテストベンチに任せるため、 このモードと定数入力を設定する --set は併用できません。

スケジュールの想定と実測の比較 ​

Execution の左側は、配置判断時に記録した組合せ回路の静的見積もりです。 演算の重み・タスクのオーバーヘッド・レーン間の同期コストから再構成し、 記録済みの候補評価値と一致することを確認します。単位は抽象的なコストであり、 実測時間を使ったり ns に換算したりしません。採用判断が記録されていれば採用候補を初期表示し、 Recorded static candidate で他の候補も選べます。

右側は選択した dispatch の実測時間（ns）です。左側の最適化前タスクは pN、 右側の実行時タスクは tN と表示します。同じ番号でも同じタスクではありません。 実行時には FF 処理が含まれる場合もあり、右側に実測フェーズを表示します。 各タスクをクリックすると、その段階の詳細を確認できます。 Dispatch を変更しても左の静的見積もりは変わりません。

古い schema 1 の記録にある Rust Debug 形式の候補タスクも読み込めます。 必要な記録がない場合や評価値が一致しない場合は、その旨を表示し、実測値で代用しません。 既存 HTML は scripts/render-parallel-report.mjs で再生成してください。

Task lineage 表で、採用された p から記録済みの unit 番号を経由して t を追えます。 どちらかにマウスを合わせると、分割・結合を含む対応先をすべて強調します。 クリックすると unit 単位の対応を表示します。実行タスク表では FF のみの場合や 組合せ処理と FF が混在する場合も区別します。これはコンパイル時の由来であり、 最適化後に残った命令の割合や p ごとの実測時間を表すものではありません。

schema 1 では、現在の最適化処理が組合せ unit の配列順を保持する契約を使います。 lowered_task.units と Comb の compiled_task.units は同じ配列を参照し、 Fused はその末尾に FF unit を追加します。候補の採用記録・ソース item・scope・ unit の網羅性・レーン・Comb の構成を検証してから対応を表示します。 未採用候補や曖昧・不完全な記録では対応を推測せず、理由を表示します。 将来 unit 自体を並べ替え・置換する最適化を導入する場合は、この由来の契約も更新が必要です。

タイムラインのタスクまたはタスク表の行をクリックすると Timeline focus を有効にします。 元のタイムライン上で選択タスクと対応先を金色、前のタスクを青、後のタスクを紫で強調し、 無関係なタスクを薄くします。左右それぞれ選択位置まで拡大・スクロールし、 全体ミニマップの白枠で表示中の範囲を示します。マップのクリックで移動でき、 倍率の指定や Locate selection で選択位置に戻る操作もできます。 前後のタスクのボタンでたどり、Back で前の選択に戻れます。

範囲は1〜3段、方向は前／後／両方を選べ、同じレーン内の順序を含めるかも切り替えられます。 任意で開ける依存図には時間軸がなく、実線は完了カウント待ち、破線はレーン内の実行順です。 レーン内の順序は必ずしも直接のデータ依存ではありません。 Full timeline で全体表示に戻り、dispatch や候補を変更すると選択と履歴をリセットします。

長い待ちを、待ち先タスクと物理メモリの衝突まで逆引きできます。

sh
node scripts/analyze-parallel-waits.mjs work/heliodor-4core/report.json

同じディレクトリの wait-analysis.html で依存待ちを順位付けし、待ち先の完了までと 完了後の通知・確認の時間を分離します。行を選ぶと実際の RAW / WAR / WAW の範囲、 重なる信号名、コンパイルされたユニットを確認できます。記録が欠けた場合は不整合として 表示します。信号名は別名も含む候補であり、ストライドを持つ配列では正確なアドレス対応に ならない場合があります。物理的な順序制約がそのまま回路本来の依存とは限りません。 複数レーンの待ち時間の合計は、実行時間や削減できる時間ではありません。

組合せ回路のタスク境界は、無制限に結合する案と、同期コストの32倍・16倍を 上限にする案を比較して選びます。各案の追加タスクと待機のコストも推定に含めます。 強制並列化で同期コストが0の場合も、上限の基準値を最低1として有限の候補を残します。 上限より大きい不可分の項目は、そのまま1タスクになります。候補表の Task budget と partition_decision.task_budget で選択理由を確認できます。 物理依存を求めた後は、各消費側について、他の各レーンで必要な最後のユニットに 完了通知点を設けます。それ以前の通知点は別の消費側が必要とする場合だけ保持し、 後続の無関係な処理による通知の遅れと不要な通知の増加を防ぎます。タスクや待機の数が増えても、 必要な結果が早く届けば実行が短くなる場合があります。効果はトレース無効の反復測定で 確認してください。
