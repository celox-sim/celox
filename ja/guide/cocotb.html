celox CLIでcocotbを使う ​

CeloxはVerylまたはSystemVerilogの設計を、VPI経由で通常の cocotb テストを実行できるネイティブ実行ファイルへ コンパイルできます。生成物にはコンパイル済み設計とCeloxランタイムが含まれるため、 実行時にHDLソースは不要です。

CLIをビルドする ​

現在、CLIはCeloxのソースツリーからビルドします。

sh
cargo build --release -p celox-vpi --bin celox

後述のrunコマンドにはPythonは不要です。VPIテストを使う場合は、利用するPython環境へcocotbをインストールします。

sh
python3 -m pip install cocotb

リポジトリのdevcontainerにはcocotb 2.0.1とVerilatorがあらかじめ入っています。

HDLテストベンチを直接実行する ​

SystemVerilogのテストベンチとVerylのnative #[test]モジュールを、同じコマンドで実行できます。

sh
target/release/celox run src/types.sv src/Dut.sv test/Top.sv --top Top
target/release/celox run test/Top.veryl --top Top

SVは.svまたは.vをコンパイル順に指定します。既定では2値シミュレーションを使い、 $finishまたは実行待ちイベントがなくなるまで実行します。 X/Zを保持する場合は--four-stateまたはcelox.tomlのfour_state = trueを指定します。 Verylはプロジェクト内の1ファイルを指定すると、Veryl.tomlから ソースと依存関係を収集します。単独のVerylファイルも使用でき、Verylも既定は2値です。 --topにはnative testbenchのモジュール名を指定します。 既存のnative testbench実行器を使うため、initialブロックの末尾への到達でも完了します。

実行できる構文は既存フロントエンドの対応範囲に従い、未対応構文にはコンパイル診断を返します。 -O O0、-O O1、-O O2で既存コンパイラの最適化レベルを選択できます。 両言語の既定値は不要なストアの削除を含むO2で、HDL testbenchが読む信号は自動的に保持します。 -Oを明示すると、その指定を優先します。

正常終了は終了コード0、コンパイル・実行エラー、アサーション失敗、$error、 $fatal、実行時イベントの欠落、実行上限による打ち切りは1、引数エラーは2です。 SVの$stopも、対話デバッガーを持たないため終了コード1になります。 SVの$display/$writeは標準出力、VerylのHDL出力は既存実行器に従って標準エラー出力に送ります。

--max-steps Nで正の実行上限を指定できます（既定値1000000）。 SVではスケジューラのステップ数、Verylではtestbenchのtick数です。 Verylでは完了前にtick上限に達すると失敗します。 コンパイルや1ステップ・tick内の処理時間は制限しないため、実時間の制限が必要な場合は 外部のタイムアウト機能を使ってください。1回の実行で言語を混在させることはできません。

SVのtestbenchでは、+で始まる位置引数（または繰り返し指定できる--plusarg +ARG）はソースではなくplusargです。 $test$plusargsと$value$plusargsはコマンドラインの順に参照します（全バックエンド対応）。

sh
celox run tb.v --top tb +iterations=9 --plusarg +trace

DPI-C で C 関数を import する SystemVerilog 設計では、関数を提供する共有ライブラリを --dpi-lib PATH（繰り返し可）、またはcelox.tomlのルートかターゲットの dpi_libs = ["lib/model.so"]で指定します。import はその C 名を定義する最初の ライブラリにリンクします。順序はルート、ターゲット、コマンドラインです。 C ソースからのライブラリのビルドはプロジェクト側で行います（svdpi.hは Celox に 含まれません）。対応する引数型は DPI-C importsを参照してください。

sh
cc -shared -fPIC -o model.so model.c
celox run tb.sv --top tb --dpi-lib model.so

両言語とも--backend native|tiered|interpreter|cranelift|wasmで実行方式を選べます（既定native）。 tieredはインタープリターで開始し、待機中のイベントを保ちながら生成コードへ移行します。 両言語とも--threads N（1〜64、既定1）で並列度を指定できます。 --unlimitedで実行ステップ・tick数の上限を解除します。

sh
celox run test/Top.sv --top Top --backend tiered --threads 4
celox run --project /path/to/veryl-project --top smoke --backend tiered --threads 4
celox run test/Top.veryl --top Top --four-state
celox run --project /path/to/veryl-project --top smoke --report --unlimited

SVのtestbenchでは、実行中に状態ファイルを保存して celox state dump/celox state diffで2つの実行やシミュレーターを比較できます（全バックエンド対応）。 --save-state-on SIGNALで数える信号（tb.clkのような階層パス、トップモジュール名は省略可）を指定し、 --save-state-at N[,M...]で保存するサイクル（1から数える）を指定します。 サイクルは、終了時に信号が1で、直前のタイムステップの終了時には1でなかったタイムステップです。 ファイル<SIGNAL>-<N>.stateはそのタイムステップの全リージョンが終わった直後に書くので、ノンブロッキング代入の更新も含みます。 --save-state-at-time T[,U...]は時刻T以前の処理をすべて終え、Tを越えて進む前の状態をtime-<T>.stateに保存します（単位はデザインのグローバル時間精度）。 --save-state-dir DIRで出力先を指定します（既定はカレントディレクトリ）。 実行が指定のサイクルに達しなかった場合はエラーです。

sh
celox run c906.v --top tb --save-state-on tb.clk --save-state-at 1000,2000 --save-state-dir states

Veryl用の--reportは設定・コンパイル時間・実行時間・tiered昇格統計・結果を 機械可読なCELOX_*レコードとして標準出力に出します。通常実行では出しません。 Heliodorベンチも専用Celoxバイナリではなく、このCLIを呼びます。 --report --backend tiered --require-compiledでは生成コードの実行を必須にできます。 通常の短いtiered実行はインタープリターのまま終了しても成功です。

--projectはcelox.tomlのほか、VerylプロジェクトディレクトリやVeryl.tomlを受け取ります。 --source-file PATHはプロジェクトからの相対パスでVerylソースを選択します（複数指定可）。 native用の--build-cache-dir DIRはVeryl.tomlプロジェクトのコンパイルをキャッシュし、 --compile-only --native-image-output FILEでイメージを書き出し、 --native-image-input FILEでHDLソースなしに実行できます。 --dump-ir-dir DIRでIRを保存し、--dump-ir-and-runでそのまま実行できます。

複数ファイルのプロジェクトを管理する ​

共通の入力と名前付きターゲットをcelox.tomlに保存できます。

toml
sources = ["rtl/pkg.sv"]
filelists = ["rtl/design.f"]
include_dirs = ["include"]
default_target = "smoke"

[defines]
SIMULATION = "1"

[diagnostics]
mixed_timescale = "warn"

[targets.smoke]
sources = ["test/Tb.sv"]
top = "Tb"
opt_level = "O1"
max_steps = 1000000

[targets.dut]
top = "Dut"

runとvpi buildは同じソース一覧、includeディレクトリ、マクロ、topを読みます。

sh
celox run --target smoke
celox vpi build --target dut -o build/dut-sim
celox run --project /path/to/celox.toml --target smoke

ソースや-fを指定しない場合、または--targetを指定した場合は、現在のディレクトリから 親方向へcelox.tomlを探索します。--project FILEで直接指定することもできます。 TOML内の相対パスは、ターゲット内も含めてTOMLのあるディレクトリを基準にします。 ソースや-fだけを指定した場合は、近くのTOMLを自動では読みません。

ターゲットはルート設定を継承します。ソースの順序は、ルートのsources、 ルートのfilelists、ターゲットのsources、ターゲットのfilelists、 CLIのソースと-f（引数に指定した順）の順です。各一覧内の順序を保持します。 includeディレクトリも同じ階層順で追加します。マクロは実行全体に適用し、 後の定義が優先されます。CLIの-Dは最後に適用します。TOMLのマクロ値は文字列です。 設定されたマクロは各ソースに適用し、HDL内のマクロ定義は既存のファイル単位のスコープに従います。 --topは選択されたtopを上書きし、runの-Oと--max-stepsはターゲット・ルートの 実行設定を上書きします。VPIビルドは既存のforce対応コンパイル設定を使用します。

--targetを省略すると、default_target、ルートのtop、唯一のターゲットの順に選びます。 複数ターゲットがあり既定値もない場合は--targetが必要です。 単独の.verylエントリーファイルをプロジェクトに指定することもでき、 Veryl側のソース探索には引き続きVeryl.tomlを使います。

コンパイル時の診断レベルは [diagnostics] で設定でき、[targets.NAME.diagnostics]、両コマンドの --diagnostic CODE=allow|warn|error の順に上書きできます。CLI オプションは繰り返し指定できます。緩和時の動作と使用例は 診断設定 を参照してください。

ファイル一覧を直接使う ​

sh
celox run -f test/all.f --top Tb
celox vpi build -f rtl/design.f --top Dut -o build/dut-sim

.fには空白区切りのソースパスを記述し、別の一覧やプリプロセッサ設定も指定できます。

text
# 相対パスはこのファイルの場所を基準にします。
../rtl/pkg.sv
-f ../rtl/design.f
+incdir+../include
+define+SIMULATION=1
"../test/with spaces/Tb.sv"

対応するオプションは-f FILE、-I DIR/-IDIR、 -D NAME[=VALUE]/-DNAME[=VALUE]、+incdir+DIR[+DIR...]、 +define+NAME[=VALUE][+NAME[=VALUE]...]です。値のないマクロは1になります。 パスには引用符やバックスラッシュのエスケープを使えます。 トークンの先頭にある#・//による行コメントと、/* ... */コメントに対応します。 ネストした一覧の相対パスは、それぞれの一覧があるディレクトリを基準にします。 環境変数・ワイルドカード・シェルの展開は行いません。 未対応オプション、未知のTOMLフィールド、一覧の循環参照はエラーにします。 CLIからも-I/--include-dirと-D/--defineを直接指定できます。 include・マクロ指定にはSV入力が必要です。

設計をコンパイルする ​

Verylプロジェクト内のソースを1つ指定し、トップレベルモジュール名を渡します。

sh
target/release/celox vpi build src/Top.veryl --top Top -o build/top-sim

Celoxはソースの位置からVeryl.tomlを探し、プロジェクトのソースと依存関係を まとめてコンパイルします。Verylプロジェクト外の単独ソースを指定した場合は、 そのファイルだけをコンパイルします。-oを省略した出力先はcelox.outです。

SystemVerilogでは1つ以上の.svファイルをコンパイル順に指定します。

sh
target/release/celox vpi build src/types.sv src/Child.sv src/Top.sv --top Top -o build/top-sim

Celoxが対応するSystemVerilogの範囲で、指定したファイルをコンパイルします。 package定義は利用側より先に指定してください。Veryl.tomlや追加のSystemVerilog ソースは自動探索しません。複数指定時はすべて.svファイルにする必要があります。 Verylではプロジェクトの入口となるファイルを1つ指定します。 celox-vpi-compileも同じソース一覧を受け付けます。

プロセスを含む設計 ​

遅延やシステムタスクを含むinitialブロック、遅延やイベント制御を含むalways ブロック、always #5 clk = ~clkのようなクロック生成など、プロセスを含む SystemVerilog設計は時間付きシミュレーションとしてコンパイルされます。生成した 実行ファイルはそのプロセスをcocotbと歩調を合わせて実行します。cocotbのタイマーと 設計の遅延は同じ時間軸を共有し、設計の$display/$write出力と$finishは celox runと同様に動作します。プロセスを含まない設計は従来どおりコンパイル されます。

1つのタイムステップの中で、cocotbが待つVPIコールバックは次の時点で実行されます。

cocotbのトリガー(VPIコールバック)実行される時点
Timer(cbAfterDelay)、NextTimeStep(cbNextSimTime)タイムステップの開始時、設計のプロセスより前
RisingEdge、FallingEdge、Edge(cbValueChange)値を変えた更新の直後。プロセスの実行、cocotbまたは設計が駆動するクロックのエッジ、フリップフロップの確定、ノンブロッキング更新、それらを読む組み合わせ回路の評価
ReadWrite(cbReadWriteSynch)タイムステップが落ち着いた後。ここでの書き込みは同じ時刻に再び落ち着かせます
ReadOnly(cbReadOnlySynch)タイムステップの終わり。ここでの書き込みは拒否されます

値の変化のコールバックは、変化のたびに、シミュレーションが先へ進む前に実行されます (IEEE 1800-2023 38.36.1、4.10)。したがって、クロックやリセットのエッジは、cocotbと 設計のどちらが駆動しても、それが起動するフリップフロップの確定より前に通知されます。 レジスタの変化は、それを読む組み合わせ回路が追従する前に通知され、追従した変化も 続けて通知されます。変化は、それで起こされるプロセスが実行される前に通知されます。 パルスは、その更新が分かれていれば2つの変化として通知されます。別のプロセスでの 更新、遅延や#0をまたぐ更新、ノンブロッキング領域をまたぐ更新がそれにあたります。

ここではプロセスの1回の実行が1つの更新です。x = 1; x = 0;のように、プロセスが 中断するまでに続けて行う代入は、その実行が残した値で1回だけ通知されます。

cocotbからの書き込みは現在時刻のブロッキング代入です。タイムステップの領域の外、 たとえばTimerコールバックの中での読み出しは格納された値を返します。同じコール バックでの書き込みから組み合わせ回路が導く値は、タイムステップが落ち着くまで 以前の値のままです。

プロセスを含む設計に対応しているのはcelox vpi buildだけです。celox-vpi-compile とそのcelox-vpi-runtimeは引き続きこれらを拒否します (#1983)。

実行ファイルには対話モードがないため、$stopはvpiStopと同様に実行を終了します。 一時停止への対応は#1886で 扱っています。

SystemVerilogのコンパイル単位 ​

既定では、指定順のソース群を一つのコンパイル単位として処理します。 ソースやヘッダーのマクロ定義、undef、コンパイラ指令、コンパイル単位の宣言が 後続ファイルに引き継がれます。--separate-units、または celox.tomlの ルート・ターゲットにsingle_unit = falseを指定すると、ファイルごとに分離します。--single-unitはプロジェクトの分離設定を上書きします。 両方式は IEEE 1800-2023 3.12.1 に従いますが、仕様は既定方式を定めていません。 この設定はrunとvpi build で使えます。Rust のソース一覧 API はファイル単位の スコープを維持し、celox_sv_analyzer::syntax::preprocess_sources` で単一単位の 前処理を明示できます。

SystemVerilog ソースと include ヘッダーでは、コメント中の非 UTF-8 バイトを デフォルトで許容します。不正なバイトは空白に置き換え、正しい UTF-8 とソースの バイト位置は保持します。文字列とコードには引き続き UTF-8 が必要です。 --strict-source-encoding、または celox.toml のルート・ターゲットに strict_source_encoding = true を指定すると、ファイル全体に UTF-8 を要求します。

sh
celox run -f rtlmeter.f --top tb --four-state

cocotbを実行する ​

たとえばtest/test_top.pyにcocotbテストがある場合、そのモジュールをimportできる 状態で生成物を起動します。

sh
PYTHONPATH=test build/top-sim --test-module test_top

生成された実行ファイルは自動的に次を行います。

  • python3からcocotbのVPIアダプターとlibpythonを検出する
  • コンパイル済みのトップレベル名をcocotbへ渡す
  • results.xmlを出力し、テスト失敗時は非ゼロで終了する

別のPython環境や結果ファイルを使う場合は明示できます。

sh
build/top-sim \
  --test-module test_top \
  --python .venv/bin/python \
  --results-file build/results.xml

--test-filter REGEXで一致するテストに絞れます。cocotbの従来形式向けに --testcase NAMEも利用できます。--vpi PATHを指定するとVPIアダプターの自動検出を 上書きします。既存の自動化向けに、PYGPI_PYTHON_BIN、LIBPYTHON_LOC、 CELOX_COCOTB_VPI、COCOTB_TEST_MODULES、COCOTB_TEST_FILTER、 COCOTB_RESULTS_FILEも引き続き利用できます。

現在の互換範囲 ​

cocotb 2.0 / 2.1 のモジュール・信号の探索、拡張識別子、スカラー・ベクター値、 packed bit handle、unpacked array の要素、real 値、string のバイト列に対応しています。 immediate deposit とゼロ遅延 inertial 更新を利用できます。packed 変数ではベクター全体の force/release と、force 中のビットへの deposit に対応しています。string の force/release と 遅延 VPI 書き込みは未対応です。Start、ReadWrite、ReadOnly、NextTimeStep、Timer、 ValueChange、End の各コールバック領域に対応しています。

upstream 回帰テストの実行手順から、 固定したバージョンの未改変 cocotb テストを生成バイナリで実行できます。 デフォルトの23構成で534件成功、upstream のスキップ5件を確認しています。 bridge スレッドからの時刻取得、force/release、2種類の inertial-write 設定を含みます。 残りの upstream グループと未対応項目は実行手順の一覧で追跡しています。
